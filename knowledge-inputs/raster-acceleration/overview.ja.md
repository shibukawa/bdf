# ラスタライズ高速化の案と、明示的な品質指定

整理日: 2026-10-14。明示的なAA指定、非AA描画経路、CLI、テストを実装した。既定の画質は維持し、既存3文書のwarm描画を72/300dpiで比較した。構造化した正本は `.knowledge/concepts/` の関連 YAML、根拠一覧は [evidence.md](evidence.md)。

## 決まった方針

利用者の最終指定は「明示的指定で良い」。**dpiによる自動切り替えは採用せず、未指定では今まで通りのAAを維持する。** 高解像度の印刷などで速度を優先する呼び出し側が、AA省略を明示的に選ぶ。

当初の「100dpi未満は画面向け、それ以上は速度重視」という案は、現在の要件ではない。100dpiは品質保証の境界ではなく、将来の比較実験で使える候補値として残す。HiDPI画面ではズームとDPRによって描画倍率が上がるため、dpiだけで印刷用途とは判定できない。

今回実装した範囲は明示指定と既定互換、真の非AA走査線経路まで。キャッシュ・解析的AA・SIMDなどの追加案は未実装として区別する。

## 実装した品質指定

`imagebdf.Options` に `Antialias AntialiasMode` を追加した。

| 値 | 動作 |
| --- | --- |
| `AntialiasDefault`（ゼロ値） | 現行のAAを維持。dpiやDPRで切り替えない |
| `AntialiasOn` | AAを明示的に使う。初期実装では現行方式 |
| `AntialiasOff` | 図形・文字・幾何クリップの境界を画素中心で判定する非AA経路 |

この三値で、ゼロ値で既存の利用者を保ちつつ、設定の上書きでも「未指定」と「明示的にON」を区別できる。`bool` ではゼロ値falseが既定のAA維持と衝突する。`*bool` も表現可能だが、列挙型の方が呼び出し箇所で意図を読みやすい。

公開APIの利用例。

```go
// 画面プレビューなど: 既定の画質を維持
preview := imagebdf.New(doc, nil)

// 高解像度の印刷向け画像: 呼び出し側が速度を選ぶ
printRenderer := imagebdf.New(doc, &imagebdf.Options{
    Antialias: imagebdf.AntialiasOff,
})
img, err := printRenderer.PageDPI(view, 0, 600)
```

CLIは `bdf render -antialias=default|on|off`。指定なしでは従来のAAを維持する。設定はRenderer単位で、未知のGo列挙値はAAを維持して警告し、未知のCLI値は入力を開く前にエラーにする。サムネイルや変換時プレビューの既定は変えていない。

`Quality=Speed/Quality` や `PrintFast` などのプリセットは将来の追加案。最初はAA指定だけに絞り、実測で複数の設定をまとめる必要が出たら導入する。その場合も明示AA指定をプリセットより優先し、バックエンド選択とは分ける。

## 非AA経路で省ける仕事

AAありの経路はY方向に1画素あたり16本の走査線を置き、X方向は被覆長を計算している。`subSamples=1` に変えるだけではX方向のAAが残る。

実装した非AA経路は、各行の `y+0.5` で辺の交点を求め、画素中心が内部の整数区間を塗る方式。区間 `[xa, xb)` に対し、左端を `ceil(xa-0.5)`、右端の排他的境界を `ceil(xb-0.5)` とする規則を使う。端点・共有辺・負座標・自己交差・EvenOdd/NonZeroは同じ規則で検証する。

第1段階として既存マスクを0/1で埋める実装を採用した。これは交点の反復・部分被覆の積算を減らすが、外接矩形全体のマスク確保は残る。第2段階で整数スパンを直接合成すれば、マスク生成と読み戻しも省ける。曲線の分割、stroke輪郭生成、画像処理、合成、出力符号化は残るため、全体16倍の高速化は予測しない。

パス、文字、stroke、矩形専用経路、幾何クリップ、画像の外周、ネストしたSVGへ設定を適用した。SVG内の独立した走査もRenderer経由へ統一し、SVGラスタのキャッシュキーに解決したAA方式を追加した。矩形の非AA被覆は暗黙の全面被覆で表すため配列を作らない。

## 画質設定から独立させるもの

| 対象 | 現在の動作 |
| --- | --- |
| 図形・文字・幾何クリップの境界被覆率 | AA指定の対象 |
| 元の色のalpha、global alpha、ブレンド、透明グループ | 維持 |
| soft mask、影・ぼかし・フィルタ | 維持 |
| 画像内部の補間、mipmap | 維持。必要なら別の明示指定を検討 |
| 1画素未満の線の幅補償 | 現状維持。厳密な二値が必要な用途は別途判断 |
| 色空間、RGBA8/float32、量子化、網点処理 | 別の設計と検証 |

非AAは輪郭の被覆率を二値にする指定であり、文書全体の1bit化ではない。現状の細線は1画素幅に広げ、元の幅をalphaへ反映するため、AAを切ってもこの補償は残り得る。バーコード、CAD、罫線で厳密な二値が必要なら、細線方針を別途検討する。

影・ぼかし・soft maskを「維持する」とは、それらの処理・設定・意味を無効化しないことを指す。OFFで元の幾何マスクが変われば、その影やmaskの画素も変わり得る。OFFとONの画素一致は要求しない。

## 集約した高速化手法

明示非AAに加え、他の全候補も隔離試作・反例・実機backendで限定評価した。[AA以外の検証結果](results-non-aa.ja.md)に速度、画素差、採用条件をまとめた。下表は候補の分類であり、通常実装への採用状況と実験結果を区別する。

| 手法 | 主に減らす仕事 | 適した場面・注意点 | 現状／優先度案 |
| --- | --- | --- | --- |
| 明示的な非AA走査 | 16重走査、部分被覆の積算 | 高解像度印刷、線画。細字・斜線は実出力で比較 | 実装・72/300dpiで測定済み |
| グリフマスクキャッシュ | 頻出文字の曲線分割と走査 | 文字主体の文書、同倍率の再描画 | 文字列全体cacheを測定。単純なglyph mask合成には反例 |
| 行スパン・RLE・疎なカバレッジ | 密な外接矩形マスクの確保・読み書き | 空白の多い文字列、大きな図形 | RLE/span試作を検証。通常実装は密なfloat32 |
| 小マスク／大領域スパンの切替 | 小図形の呼び出し負担、大図形のマスク負担 | Skiaの大きさ別経路が参考 | A8試作を測定。固定閾値の優位性は未確立 |
| 解析的AA | サンプリングによる走査反復 | AAを維持する画面描画。境界画素は変わり得る | Skia・AGG・Blend2Dが参考。別の比較候補 |
| 単色・不透明・矩形・凸図形の専用処理 | 汎用合成、分岐、安全な加算の処理 | 頻度の高い単純図形 | 矩形は既存。追加特殊化・凸形状を隔離評価 |
| SIMD、処理段の融合 | 画素演算、色と被覆率の中間転送 | 大面積の合成、グラデーション | NEON・融合試作と外部pipelineを測定 |
| 通常描画をRGBA8、必要な層だけfloat | 16B/画素の作業画像と最終変換 | 高dpiの大画像 | 全RGBA8とfloat層混用を検証。精度反例あり |
| 曲線分割・stroke展開の再利用 | 同じ幾何の前処理 | 同倍率の繰り返し、アイコン、数式 | flatten/stroke cache・適応分割を比較済み |
| タイル・帯ごとの並列化 | 大ページの経過時間、作業メモリ | 高dpiページ、多ページバッチ | ページ並列は有望。Region分割には影・丸め差 |
| ページ・領域・オブジェクト画像のキャッシュ | 再描画全体 | 静的なプレビュー、数式 | Page/Region/Object再利用とコピー費用を測定 |
| Skia / Blend2D / Vello CPUの比較 | バックエンド全体 | ネイティブ依存を許容できる環境 | 共通図形を実測。一般BDF adapterは別工程 |
| GPU、CPU/GPUハイブリッド | 動的な大量描画の画素処理 | 画面表示 | Metal実機でupload/readback込みを測定 |
| ベクタPDFのまま出力 | アプリ側のページ全体のラスタライズ | PDFを受け付ける印刷経路 | PDF生成とGhostscript後段を測定。実機印刷は未検証 |

Skiaの参考点は、解析的AAだけではない。小さい図形の固定A8マスク、大きい図形の行RLE、凸形状の専用走査、単色不透明の一括書き込み、グリフ画像のキャッシュ、事前コンパイル済みSIMD処理段の組み合わせがある。Blend2DはJITで処理を特殊化する。VelloのSparse Stripsは輪郭付近の被覆率と完全被覆の内部を異なる密度で表す。いずれも「常に最速」という比較結論にはしない。

## キャッシュとバックエンドの契約

グリフ・SVG画像・ページ画像のキャッシュキーには、実際に解決したAA方式を含める。加えてフォント内容、グリフID、倍率・変換、小数画素位置、合成太字・斜体、その他出力に影響する設定を扱う。再利用率とメモリ上限を同時に測る。

描画開始時に設定を解決し、ページ内のオブジェクトの拡大率で勝手にAAを切り替えない。ブラウザCanvas 2Dで任意パスのAAを同じように無効化できるとは仮定せず、今回の第一対象はGoの `raster/imagebdf` とする。別バックエンドが設定を満たせない場合の通知・エラー方針は追加時に定義する。

## 最初の検証のまとまり

「既定互換のAA指定＋真の非AA経路＋少数の比較ページ」を実装した。次の検証軸は以下。72/300dpiのwarm描画、既定の画像ハッシュ、各APIと設定伝搬・合成・複雑度制限をテストした。その他の解像度・cold起動・実機印刷等は追加評価として残す。

1. 既定／明示ONが現行goldenと一致し、dpiに連動しないことを確認する。
2. OFFがパス、矩形、文字、stroke、幾何clip、画像外周、SVGへ伝搬し、塗り規則・共有辺・負座標を保つことを確認する。
3. 透明・soft mask・影・画像補間・細線補償の処理や設定を意図せず無効化しないことを確認する。非AAの幾何マスクに由来する影などの画素差は許容して評価する。
4. 日本語を含む文字主体、複雑な図形、大きな塗り、透明と画像を含む少数ページを72/96/100/144/300/600dpiで比較する。1200dpiは画素数上限とメモリを確認して追加する。
5. 描画のみのcold/warm、PNG符号化込み、CPU時間・経過時間・alloc・ピークメモリを分ける。画像差だけでなく、細字・細罫線・斜線・コードの読み取り・実寸印刷も評価する。

100dpi付近の画像は境界品質の観察用であり、自動切り替えの受け入れ条件ではない。今回の測定結果は次節に保存した。過去のM3ベンチ記録は現状理解の根拠であり、今回の変更後の測定結果ではない。

## 残した質問

- 公開APIは `Options.Antialias`、CLIは `-antialias`、Renderer単位で実装した。描画単位の上書きは具体的な利用例が出たら検討する。
- 細線補償を維持する実装で、帳票・コード・CADの要件を満たせるか。用途ごとの実機出力を評価できた時点で再検討する。
- 初期実装は非AAマスク方式を採用した。整数スパン直接合成は、残る確保量と合成負荷のプロファイルから検討する。
- グリフキャッシュの小数位置の量子化、メモリ上限、stroke文字の扱い。文字主体の測定で効果が見えたら決める。
- 品質プリセットやバックエンド選択を公開する必要があるか。複数の改善を組み合わせる段階まで延期する。
- dpi自動選択は現在採用しない。利用者が再度求めた場合だけ、用途・最終物理サイズ・HiDPIを含めて再検討する。
