# ノードの種類 {#node-kinds}

すべてのノードに種類があり、種類ごとの設定があります。入口（アップローダー、CUPS サーバー、S3 トリガー）は外から文書とデータを受け取ります。キュー、クラス、フィルタ、アサート、ブランチ、インボックスは振り分けます。テンプレートノードと変換ノードは文書を作り、署名ノードは文書に署名します。ディスプレイ、プリンタ、CUPS サーバーのキュー、アーカイブ、シンクはジョブの行き着く先です。インボックスかアーカイブの後ろのダウンローダーは、アプリケーションや人がジョブを取りに来る場所です。HTTP (push) ノードはジョブを Web サービスへ送ります。IPP が入ってくるのは CUPS サーバーノードだけです（[IPP](entries.md#ipp)）。コンピュータはそこに印刷し、アプリケーションはアップローダーにファイルを POST し、バケットのイベントは S3 トリガーに届きます。それ以外のノードにはエッジを通ってだけ届きます。ノードは後ろのノードより先に置けます。下の表のエッジ（`to`、クラスの `members`）がなくても追加でき、まだどこにも送らない入口、キュー、ステップに届いたジョブは、そこでエラーになります。

## すべてのノード {#common}

| 設定 | |
|---|---|
| 名前 | ノードのシステム上の名前。英数字と `.`、`_`、`-` で、ほかのノードと重なりません。変えるとノードの名前が変わり、エッジも付いてきます（[名前・題名・説明](topology.md#names)） |
| 題名 | 人が読む名前。ノードのタイトルバーに表示します |
| 説明（`description`） | ノードが何のためにあるかのメモ。1000 文字まで。最初の数行がキャンバスのノードの中に、全文がサイドバーに出ます |
| スコープ、所有者 | ページからノードに送れる人と、そのジョブが誰のものか。`shared`（サインインした全員）、`group` で所有者にグループ、`personal` で所有者に本人のメールアドレス（[ノードのスコープ](roles.md#scopes)） |
| 失敗の行き先（`on_error`） | このノードの送りや段が最終的に失敗したとき、届いたものを持ってジョブが向かうノード。たとえば[通知](#notify)ノード。無ければ全体の既定（`docflow.on_error`）へ、それも無ければジョブはここで中止します（[失敗の行き先](#on-error)） |

サイドバーの 1 行が、ノードが受け取るものと送り出すものを示します（[ペイロードの種類](flow.md#kinds)）。

## アップローダー {#upload}

種類 `upload` のノードです。アプリケーション向けの REST の入口です。`POST /api/upload/<name>` にアップローダー自身のキーかアプリのトークンを添えると、ボディの文書、またはテンプレートノード向けのデータを受け取り、ジョブを `to` のすべてのノードへ送ります。リクエストは[アップローダー](entries.md#uploaders)にあります。

| 設定 | |
|---|---|
| 送り先（`to`） | 選んだすべてのノードがジョブを受け取ります。まだなければ、ジョブはここでエラーになります |
| 受け取るもの（`accept`） | `file`: 文書（既定）。`data`: JSON、YAML、CSV、Excel ブック、Parquet ファイル。後ろのテンプレートノード向けです |
| 送り出すもの（`output`） | 文書をどう送り出すか。`bdf` は作った `.bdf`（既定）、`file` は受け取ったままのファイル。後ろの変換ノードやアーカイブ向けです |
| 受け取る形式（`formats`） | コンバータの名前で指定します（`pdf`、`docx`、`image`、`csv`、`bdf`、`json`、`yaml` ……）。空ならすべて受け取ります。ほかの形式のファイルは拒否され（415）、拒否は監査ログに残ります |
| 加えるメタデータ（`meta`） | アップローダーが受け取るすべてのジョブに加えるキー。送り手のキーより優先します（[メタデータ](flow.md#metadata)） |
| 許可するアプリ（`apps`） | キーのほかに、自前の資格情報でここへ送れるアプリ（[アプリ](entries.md#apps)） |

キーはアップローダーを作ったときとキーを回したときに 1 度だけ表示されます。マネージャーが保存するのはそのハッシュだけです。

## CUPS サーバー（ソース） {#cups}

コンピュータや業務システム向けの IPP の入口で、IPP の入口はこれだけです。プロセス自身のポートで動く CUPS サーバーで、プリンタはノード自身の 1 台です。`lpstat -h <host>:<port> -p` で一覧でき、コンピュータは `ipp://<host>:<port>/printers/<name>` に印刷し、受け取ったものは `.bdf` にして `to` のすべてのノードへ進みます。ノードはマネージャー自身のサーバーの `/ipp/print/<name>` の IPP プリンタでもあります。ポートのないサーバーレスでは、こちらだけです。設定は [CUPS サーバーノード](entries.md#cups)にあります。

| 設定 | |
|---|---|
| 送り先（`to`） | 選んだすべてのノードが、ここに印刷されたものを `.bdf` にして受け取ります |
| ポート（`port`） | サーバーが待ち受けるポート。指定しなければ、6310 から、どのノードも使っていない最初のポート（サーバーレスでは使えません） |
| TLS 証明書、TLS キー（`tls_cert`、`tls_key`） | それぞれのファイル。あれば `ipps` になります。なければ平文の `ipp` です |
| Bonjour（`dnssd`） | プリンタを DNS-SD（Bonjour）でローカルネットワークに AirPrint プリンタとして告知します。Mac は「プリンタを追加」の「デフォルト」に、iPhone と iPad はプリントの画面に挙げます。既定で告知します。ポートがあるときだけです（サーバーレスでは使えません）。`false` にするとネットワークに出しません |
| 加えるメタデータ（`meta`） | アップローダーと同じです。Print-Job リクエストのジョブ属性はメタデータになります。`ipp.media`、`ipp.copies` …… |
| 許可するアプリ（`apps`） | id とシークレットを IPP の Basic 認証で渡して、ここに印刷できるアプリ（[アプリ](entries.md#apps)） |

コンピュータが印刷するのは文書です。CUPS サーバーにはアップローダーの「受け取るもの」「送り出すもの」「受け取る形式」がなく、作った `.bdf` を送り出します。受け取ったままのファイルを送り出したいときは、アップローダーか S3 トリガーに送ります。

## キュー {#queue}

ジョブを `to` のすべてのノードへ送ります。ほかのノードの前に置く仮想プリンタで、複数あれば分岐です。到達したものをそのまま送ります。

| 設定 | |
|---|---|
| 送り先（`to`） | ノード |

## クラス {#class}

ジョブを `members` の 1 つに送ります。順番に（`round-robin`、既定）、または先頭に（`failover`）です。ジョブを受け取らないメンバー（届かないプリンタ）は、次の試行で次のメンバーに飛ばされます。

| 設定 | |
|---|---|
| メンバー（`members`） | ノード。順番どおり。まだなければ、ジョブはここでエラーになります |
| 方針（`policy`） | `round-robin` または `failover` |

## フィルタ {#filter}

ルールでジョブを先へ送ります。ジョブに一致する最初のルールが、そのルールのノードへ送ります。どのルールにも一致しないジョブは `otherwise` へ行くか、なければそこで終わります（`dropped`）。到達したものをそのまま送ります。ルールが見るものは[フィルタのルール](flow.md#rules)にあります。

| 設定 | |
|---|---|
| ルール（`rules`） | 順番どおり。一致条件（名前、ユーザー、形式、ページ数、メタデータ、ペイロードの種類）とノード |
| どれにも合わなければ（`otherwise`） | どのルールにも一致しないジョブの行き先 |

## アサート {#assert}

ジョブのメタデータを検査します。すべてのチェックを通ったジョブは、到達したそのままの形で `to` のすべてのノードへ進みます。1 つでも通らなかったジョブはそこから先へは進まず、何が通らなかったかとともに `on_error` へ行きます。チェックが見るものは[チェック](flow.md#checks)にあります。

ジョブが送られたノード（入口か、ページや API から送られたキュー）の直後にあるアサート、またはそのノード自身がアサートなら、それは送り手に対する関門です。ジョブはどこへ行くよりも先に検査され、送り手のリクエストはチェックを通ってはじめて受け付けられます。通らなかったジョブは、何が通らなかったかを添えて送り手に拒否されます。REST なら 422、IPP なら `client-error-bad-request` です（[アップローダー](entries.md#uploaders)）。ジョブは中止（aborted）として残り、アサートに `refused` のレグが付きます。もっと先にあるアサートは、送り手に応答した後、ジョブが届いたときに検査します。そこで拒否されたジョブはそこで中止になります。

| 設定 | |
|---|---|
| 通過の送り先（`to`） | 通ったジョブの行き先。まだなければ、通ったジョブはここでエラーになります |
| チェック（`checks`） | すべてを満たさなければなりません。キーと、その値の条件です |
| 通らなかったときの行き先（`on_error`） | 通らなかったジョブが、アサートに到達したものとともに行くノード。[通知](#notify)ノードなら `{{meta.$error}}` で何が通らなかったかを伝えます。なければマネージャーの既定（`docflow.on_error`）へ行くか、ジョブはここで止まります |

キャンバスのアサートにはポートが 2 つあります。`pass` が `to`、`fail` が `on_error` です。

## ブランチ {#branch}

switch 文です。チェックをすべて通る最初のケースが、ジョブをそのケースのノードへ送り、残りのケースは試しません。どのケースにも当てはまらないジョブは `default` へ行くか、なければそこで終わります（`dropped`）。到達したものをそのまま送ります。ケースはアサートと同じように検査します（[チェック](flow.md#checks)）。

| 設定 | |
|---|---|
| ケース（`cases`） | 順番どおり。名前（`name`。ポートのラベルになり、なければ `case <n>`）、すべてを満たすべきチェック（`when`）、ノード（`to`）です。ケースは何かを検査します。ノードがまだないケースに当てはまったジョブはエラーになります |
| どのケースにも合わなければ（`default`） | どのケースにも当てはまらないジョブの行き先 |

キャンバスのブランチには、ケースごとにその名前のラベルが付いたポートと、`default` のポートがあります。ポートからドラッグすると、その枝にノードが加わります。レグにはジョブが通った枝が記されます。

## テンプレート {#template}

到達したデータでテンプレートの 1 つを埋め、帳票を `.bdf` 文書として `to` のすべてのノードへ送ります。受け取るのはデータだけです。JSON、YAML、CSV、Excel ブックです。テンプレートとデータは[テンプレートとデータ](templates.md)にあります。

| 設定 | |
|---|---|
| 送り先（`to`） | 埋めた帳票の行き先 |
| 届いたままのデータの行き先（`original`） | ノードに届いたデータを、そのまま送るノード。帳票と同じトレースが付きます（[原本とトレース](flow.md#traces)） |
| テンプレート（`template`） | 埋めるテンプレート。id で指定します。まだなければ、ノードを置いてからアップロードします（それまでに届いたジョブはここで失敗します） |
| またはテンプレートを指すメタデータのキー（`template_from`） | 代わりに、このキーの値がテンプレートを選びます（送り手の `doc-type` など） |
| リストの名前（`list_name`） | レコードの一覧（CSV ファイル、シート、JSON の配列）であるデータがテンプレートの中で持つ名前。既定はファイル名 |
| 厳格（`strict`） | テンプレートが引く名前のないデータを拒否します |

このステップは配送と同じように行われます。経路が決まった直後にプロセスが、またはティックが行います。テンプレートがない、データが読めないときは再試行せず、最終的な失敗になります（[配送](inboxes.md#deliveries)）。

## 変換 {#convert}

受け取ったままのファイル（PDF、Office 文書、画像）から `.bdf` 文書を作り、`to` のすべてのノードへ送ります。`.bdf` はそのまま送ります。JSON と YAML にはそれ自体の文書がなく（テンプレートを埋めてください）、CSV と Parquet ファイルにはまだ印刷するページがありません。このステップは配送と同じように行われます。

| 設定 | |
|---|---|
| 送り先（`to`） | 文書の行き先 |
| 届いたままのファイルの行き先（`original`） | ノードに届いたファイルを、そのまま送るノード。文書と同じトレースが付きます（[原本とトレース](flow.md#traces)） |
| 変換する形式（`formats`） | 空なら、コンバータが読めるすべての形式を変換します |

## 署名 {#sign}

届いた `.bdf` 文書に、Docflow の鍵で立会人として署名し、署名した文書を `to` のすべてのノードへ送ります。ジョブを送った人は鍵を持ちません。Docflow がその人について保証します。署名には、Docflow が見たこと（役割、ノード、ジョブ、Docflow が確かめた送り手、受け取った時刻）が入り、`bdf verify` で読めます。署名はその後の文書の変更を見つけるもので、変更を防ぐものではありません。鍵は Docflow のもので（`DOCFLOW_SIGN_KEY_FILE` と `DOCFLOW_SIGN_CERT_FILE`、タイムスタンプは `DOCFLOW_SIGN_TSA`）、鍵がなければこのノードはジョブを失敗にします。このステップは配送と同じように行われます。

| 設定 | |
|---|---|
| 送り先（`to`） | 署名した文書の行き先 |
| 役割（`sign_role`） | 署名が言う、Docflow の署名の役割（空なら `witness`） |

## インボックス {#inbox}

誰かがノードへ送り出すか破棄するまで、ジョブを留めます。人ならインボックスのページで（[インボックス](inboxes.md#inboxes)）、アプリケーションなら `/api/inbox/<name>` の API で行います（[インボックスの API](inboxes.md#api)）。送り出した項目と破棄した項目は `keep` の間表示されます。`to` にある[ダウンローダー](#download)は、インボックスがジョブを留めている間それを一覧し（保管されたファイル）、アプリケーションが取りに来られるようにします。送り出すか破棄すると一覧から外れます。インボックスを扱うのは、スコープで決まる人と、許可したアプリです（[インボックスを扱う人](inboxes.md#workers)）。

| 設定 | |
|---|---|
| 送り出せる先（`to`） | 項目を送り出せるノード。空ならどのノードにも送れますが、送り出すのは役割 topology だけです。ダウンローダーは送り出し先に入りません |
| 保持期間（`keep`） | 終わった項目を表示しておく期間（14 日） |
| 許可するアプリ（`apps`） | 自分のトークン（スコープ `inbox`）でインボックスを扱うアプリ |
| スコープ、所有者 | `group` のインボックスはそのメンバーが、`personal` のものは所有者が扱います。`shared` のものを扱うのは役割 topology です |

## ディスプレイ {#display}

ディスプレイに登録したデバイス（拠点のタブレット）にジョブを伝票として表示し、`fallback.after` の間に誰も開かなかったもの、またはデバイスが 1 台もつながっていない間のすべての未開封の伝票を、フォールバックプリンタで紙に印刷します。受け取るのは `.bdf` 文書だけです。デバイスとボードは[ディスプレイボードとデバイス](displays.md)にあります。

| 設定 | |
|---|---|
| フォールバックプリンタ、印刷までの時間（`fallback`） | プリンタと、未開封の伝票が印刷されるまでの時間。0 ならデバイスがつながっていない間だけ |
| 保持期間（`keep`） | 完了または取り消した伝票をボードに残す期間（14 日） |
| オフラインとみなすまで（`offline_after`） | デバイスが黙っていても接続中とみなす時間（2 分） |

## プリンタ {#printer}

マネージャーがネットワーク越しに届くプリンタで、ジョブを紙に印刷します。受け取るのは `.bdf` 文書だけです。失敗した印刷は再試行されます（[配送](inboxes.md#deliveries)）。

| 設定 | |
|---|---|
| URL（`url`） | `ipp://` または `ipps://`（IPP プリンタ）、`socket://host:9100`、`lpd://host/queue`。CUPS サーバーのキューには [CUPS サーバー（シンク）](#cups-out)を使います |
| Bonjour（`bonjour`） | URL を選んだときのインスタンス名。サイドバーの「接続方法」で AirPrint を選ぶと、サーバーのローカルネットワークで Bonjour が見つけた IPP プリンタ（AirPrint と IPP Everywhere のプリンタ、コンピュータが共有しているキュー）が並び、そこから選べます。手動はアドレスを入力します。こうして選んだプリンタがそのアドレスで接続を受けないと、名前で探し直し、今ある場所に印刷します（DHCP でプリンタのアドレスが変わる場合）。サーバーレスでは使えません |
| 経路（`route`） | ジョブがどうプリンタに届くか。`direct` はマネージャーが送ります（既定）。`branch`（拠点の `bdf printd` が取りに来る）はまだありません。そのプリンタへの配送は失敗します |
| プレビュー（`preview`） | 偽プリンタファームの API 上のこのプリンタの URL（`tools/fakeprinter`）。偽プリンタが受け取ったものを、ファームが読み戻したとおりにノードの横に表示します |

## CUPS サーバー（シンク） {#cups-out}

コンピュータが印刷するのと同じように、CUPS サーバーのキュー（そこのプリンタかクラス）へ IPP でジョブを印刷します。マネージャーはキューが対応すると言う PDF（または PWG Raster）を送り、CUPS サーバーのフィルタとドライバがプリンタの受け取るものにします。受け取るのは `.bdf` 文書だけです。失敗した印刷は再試行されます（[配送](inboxes.md#deliveries)）。対になる [CUPS サーバー（ソース）](#cups)は、コンピュータが印刷したものを受け取ります。

| 設定 | |
|---|---|
| サーバー（`url`） | キューの URL。`ipp://host:631/printers/<queue>`、クラスなら `/classes/<class>`、TLS なら `ipps://`。サイドバーの「キューを探す」で、サーバーにキューを尋ねて（CUPS-Get-Printers）選べます |
| Bonjour（`bonjour`） | キューを選んだときのインスタンス名。サイドバーの「接続方法」で AirPrint を選ぶと、サーバーのローカルネットワークで Mac や CUPS サーバーが共有しているキューが Bonjour で見つけたとおりに並び、そこから選べます。手動はサーバーとキューを入力します。こうして選んだキューは、[プリンタ](#printer)と同じように探し直します。このマネージャー自身の CUPS サーバーは並びません。エッジでつなぎます |
| 資格情報（`credential`） | サーバーが求めるときの `user:password`。なければ認証しません（[資格](#credentials)） |

`ipp.job-account-id` などのキーは、プリンタと同じようにキューへ渡ります（[プリンタへ渡るもの](flow.md#ipp-attributes)）。

## アーカイブ {#archive}

到達したもの（`.bdf` 文書、または受け取ったままのファイルやデータ）と、ジョブの JSON の記録（メタデータ、ペイロード、レグ）をストアに書きます。各オブジェクトは 1 度だけで、マネージャーが変更も削除もしません。バケットに既定の保持期間（S3 Object Lock）を与えれば、誰も変えられない監査証跡になります。書き終えると、ジョブは `to` のすべてのノードへ進みます。そこにあるダウンローダーがジョブを一覧に載せます（[ダウンローダー](downloads.md)）。

| 設定 | |
|---|---|
| ストア（`store`） | 文書のストア。`bbolt:path`、`s3://bucket?region=…`、`r2://bucket?endpoint=…`、`gcs://bucket` |
| コレクション（`collection`） | オブジェクトの接頭辞。既定は `archive-<name>` |
| 送り先（`to`） | 書き終えたジョブが進むノード。ダウンローダーです |

## シンク {#sink}

到達した最新の文書を保持し、トポロジーで見られるようにします。最初のページはノードに、すべてのページはサイドバーに表示されます。新しいものが来ると古いものは消えます。プリンタやデバイスなしで文書を確かめる場所です。アップローダーや CUPS サーバーを設定している間、その後ろに置きます。

| 設定 | |
|---|---|
| 保持数（`latest`） | 最新の文書をいくつ保持するか（10） |

## ダウンローダー {#download}

種類 `download` のノードです。直前のインボックスかアーカイブが保管しているもの（保管されたファイル。受け取るのはこの種類だけです）を一覧し、アプリケーションや人が `GET /api/download/<name>` で取りに来られるようにします。各エントリは、メタデータが示す所有者の下に並びます。アーカイブのものは恒久的に、インボックスのものはジョブを留めている間だけ残ります。それ以外のノードからのエッジは拒否され、ここへ印刷することはできません。誰が何を読むか、バックエンドとフロントエンドは[ダウンローダー](downloads.md)にあります。マネージャーの方から Web サービスへ送るなら [HTTP (push)](#http) を使います。

| 設定 | |
|---|---|
| 所有者のキー（`by`） | 文書が誰のものかを値で示すメタデータキー。送り手が与えた顧客の id やメールアドレスです。空なら、人はもともとジョブで見られたものを読みます |
| 主体（`subject`） | 人の何を所有者と比べるか。`email`（既定）、`sub`、`id`、`group`（[誰の文書か](downloads.md#owners)） |
| 項目（`fields`） | 一覧のエントリに写すメタデータキー。読み手が表示や選択に使います（16 個まで） |
| エントリ数（`entries`） | 全員分と所有者ごとに、最新のエントリをいくつ一覧するか（1000）。それより古いエントリも、ジョブの番号で読めます |
| 許可するアプリ（`apps`） | トークンですべてのエントリを読むバックエンド（スコープ `download`）。フロントエンドは本人として読むので、載せる必要はありません |

## S3 トリガー {#s3-trigger}

バケットに置かれたオブジェクトの入口です。バケットを待ち受けはしません。S3 のイベントを EventBridge のルール（API destination）か Lambda に送り、そこからオブジェクトの参照を `POST /api/s3-trigger/<name>` にノードのキーを添えて送ります。キーはアップローダーと同じく作られ、「キーを回す」で作り直せます。ボディは `{"bucket": …, "key": …}`、S3 の通知（`Records`、オブジェクト 1 つ）、EventBridge のイベント（`detail`）のどれかです。ノードが自分でオブジェクトを読み、ジョブはメタデータに `s3.bucket` と `s3.key` を持って先へ進みます。

| 設定 | |
|---|---|
| バケット（`url`） | `s3://bucket?region=…`。AWS 以外のサービス（MinIO、R2）には `&endpoint=…` |
| 資格情報（`credential`） | `access-key:secret-key`、または `:session-token` 付き。無ければ AWS の既定（環境変数、ロール）（[資格](#credentials)） |
| プレフィックス（`path`） | 受け取るキーの接頭辞。それ以外のキーや別のバケットは拒否します（403） |
| 送り先、受け取るもの、送り出すもの、受け取る形式、加えるメタデータ | アップローダーと同じ |

## 描画 {#render}

届いた `.bdf` 文書を PDF に、または 1 ページを PNG 画像（150 dpi）に描きます。BDF のビューアを持たない相手（メールの読み手、Web サービス）へ送る出口の前に置きます。描いたファイルは任意のファイルとして `to` へ進みます。配信と同じく裏で行います。

| 設定 | |
|---|---|
| 送り先（`to`） | ファイルを送るノード |
| 形式（`format`） | `pdf`（既定）か `png`。SVG はまだありません |
| ページ（`page`） | PNG にするページ（1） |

## 通知 {#notify}

ジョブが通ったことを知らせ、届いたものを `to` があればそこへ送ります。失敗は [on_error](#on-error) の辺からエラーと一緒に届きます。文書は送りません。

| 設定 | |
|---|---|
| 手段（`via`） | `slack`：Incoming Webhook。URL を資格に置きます。`mail`：メール。メールノードと同じ設定で、添付はありません。`http`：JSON（`text`、`job`、`name`、`node`、`error`、`error_node`、`meta`）を `url` に POST。資格は Authorization に使います |
| 本文（`text`） | 知らせる文。`{{meta.<key>}}` が使えます。既定ではジョブとノード、失敗ならノードとエラー |
| 送り先（`to`） | ジョブが続けて向かうノード |

## メール（SMTP） {#smtp}

届いたものを添付してメールで送ります。Message-ID は配信の ID で、再試行しても変わりません。

| 設定 | |
|---|---|
| サーバー（`url`） | `smtp://host:587`（サーバーが出せば STARTTLS）か `smtps://host:465` |
| 資格情報（`credential`） | `user:password`。TLS の上か、同じマシンにだけ渡します |
| 差出人、宛先、件名、本文（`from`、`recipients`、`mail_subject`、`text`） | メールの中身。`{{meta.<key>}}` が使えます |

## S3 {#s3}

届いたものをバケットに 1 度だけ書き、後は見ません。既にあるオブジェクトは書いたものとみなします。記録と一緒に残す必要があるものは[アーカイブ](#archive)へ送ります。

| 設定 | |
|---|---|
| バケット（`url`）、資格情報（`credential`） | S3 トリガーと同じ |
| キー（`path`） | `{{meta.<key>}}` が使えます。既定は `{{meta.$job}}/{{meta.$name}}`。値は接頭辞の外へ出られません（`..` と先頭の `/` を落とします） |

## HTTP (push) {#http}

種類 `http` のノードです。届いたものをリクエストで Web サービスへ送ります。文書とジョブのメタデータをどう載せるかは `body` で決まり、配信の ID は `Idempotency-Key` になります。別の Docflow へ送るなら、URL を相手の `/api/upload/<node>` に、資格を相手のキーかアプリのトークンにします。ボディはどちらでも、`.bdf` はそのまま届き、名前もメタデータも送り手のものとして受け取られます（[アップローダー](entries.md#uploaders)）。408、429、5xx は再試行し、それ以外の応答は最終的な失敗です。逆向き、つまりアプリケーションが文書を取りに来るのは[ダウンローダー](#download)です。

| 設定 | |
|---|---|
| URL（`url`） | `http(s)://…`。`{{meta.<key>}}` が使えます（値は URL 用にエスケープ） |
| メソッド（`method`） | `POST`（既定）か `PUT` |
| ボディ（`body`） | `direct`（既定）：文書をそのままボディにし、`Content-Type` と、`Content-Disposition` に名前を付けます。メタデータは `X-Meta-<key>` ヘッダで送ります。`multipart`：ボディを `multipart/form-data` にし、まずパート `meta` にメタデータの JSON オブジェクト（値は与えられたまま）、続いてパート `file` に文書を名前と型付きで入れます。どちらも、マネージャーのキー（`$…`）は送りません |
| ヘッダ（`headers`） | 追加のヘッダ。`{{meta.<key>}}` が使えます。ボディが `multipart` なら `Content-Type` と `Content-Disposition` は指定できません |
| 資格情報（`credential`） | Authorization。トークンなら Bearer で送り、`Basic …` のように方式付きならそのまま |

描画、通知、メール（SMTP）、S3、HTTP にはサイドバーの専用の欄がなく、設定は「設定（JSON）」の欄に書きます。S3 トリガーには、アップローダーと同じように専用の欄があります。

## 失敗の行き先 {#on-error}

送りや段が最終的に失敗すると（拒否、テンプレートが無い、再試行の最後）、ジョブはノードの `on_error` の辺（破線）を通り、届いたものと、次のノードから見える `$error` と `$error_node` を持って進みます。辺の無いノードの失敗は全体の既定（`docflow.on_error`、`DOCFLOW_ON_ERROR`）へ向かいます。ただし既に失敗の道にいるジョブは既定へ送りません。通知ノードの失敗が自分を知らせ続けないためです。どちらも無ければ、ジョブはそこで中止します。どの場合もジョブは中止です。辺は知らせるためのもので、直すものではありません。

## 資格と `{{meta.<key>}}` {#credentials}

ノードは資格を名前で指します（`credential`）。秘密そのものはノードと一緒に保存されません。値は環境変数 `DOCFLOW_CRED_<name>`（`-` は `_`）、無ければ `docflow.credential_dir` の中のファイル `<name>` です。出口と通知ノードの設定には `{{meta.<key>}}` が使えます。式はありません。使える鍵はジョブのメタデータ（[メタデータ](flow.md#metadata)）と、`$node`、`$delivery`、`$name`（文書の名前）、`$error`、`$error_node` です。無い鍵は空になります。ヘッダは改行を、キーは `..` を落とします。出口はどれも少なくとも 1 度送ります。結果の分からない送りは同じ配信の ID でもう 1 度送るので、相手はそれで見分けます。
