# Print Manager のトポロジーを汎用のドキュメント変換フロー（ETL）に広げる案（2026-10-21）

2026-10-21 の利用者の構想を `/knowledge-memory` で整理した叙述。要件の概念は `.knowledge/` の `requirement:document-flow`（問いと暫定の選択はそこ）。土台は `milestone:pm-4`（トポロジー）、`milestone:pm-4b`（filter）、`milestone:pm-5c`（入口のポート、cups、sink）と `requirement:print-manager-console`。

利用者「Printer Manager のトポロジーにはもっと大きなポテンシャルがあることに気づいた。データベースを想定しない、汎用の ETL フローというかドキュメント変換フローとして使える。そのためにエッジやその接合部に種類を設けたい。BDF ファイルのみが流れるエッジやコネクタ、JSON/YAML/CSV/Excel/Parquet といった『データ』のコネクタ、あるいはそれ以外も流れるコネクタの 3 種類。API エンドポイント、CUPS サーバーはファイルを受けるが、コンバートフラグを持っており、それにより出力が BDF かそれ以外が変わる。API はデータのみを受けるフラグがあれば出力はデータになる。データはテンプレート変換ノードを使って BDF にできる。API では追加のメタデータも送付でき、それをパラメータに使って変換処理でテンプレート選択を行ったりできる。また、コンバートノードでそれ以外のデータを BDF に強制キャストできる。プリンタ印刷ノードの入力は BDF のみとする。また、外部 CUPS サーバーへの送信なども。メタデータを使った条件分岐もできるようにする。ブランチノードは複数の枝を増やせる。入力のデータ種によって出力のデータ種も変わる。アーカイブノードはどの様なデータ種でも扱える。入出力ノードとしては、SMTP や FTP(S)、S3（イベントトリガー）も提供する。データ変換ノードなども提供する。これはアプリが任意で拡張できる仕組みを作る」。

## 0. 今の形（2026-10-21 の main、#126 まで）

- ノードの種類は endpoint・cups・queue・class・filter・inbox・archive・display・printer・sink。辺は名前だけで指す（`To`・`Members`・規則の `to`・`Otherwise`・`Fallback`）。PUT で存在・名前の重なり・閉路を確かめる。
- **ジョブは文書 1 つで、中は必ず `.bdf`**。入口（`submit.go` の `document()`）が形式を見分けて変換器で `.bdf` にしてから Job を作る。`Job.Format` は元の形式の名で、filter の `format` の規則はそれを見る。
- エンドポイントは `accept`（file / template / both）と `formats`（受ける形式の一覧）を持ち、テンプレートはエンドポイントの持ち物（pm-5 で利用者が選んだ）。差し込みの入力は JSON の `data` だけ（`form.LoadData` は JSON・YAML・CSV・XLSX を読める）。
- プリンタと保管への送りは Delivery（借り、再試行 20 回、プロセスは背景・サーバーレスは tick）。経路のノード（queue・class・filter・inbox）は要求の中で即座に辿る。
- 制約：インスタンスに状態を持たない、常駐に頼らない、保存は yuruidb（記録 256 KiB、大きいものは Blob）、各社の SDK を同梱しない、yuruidb に取り出して使える秘密を置かない。

つまり今は「型が 1 つ（BDF）しかない」ので型検査が要らず、「変換は入口で 1 回だけ」なので変換の段が要らない。広げると、この 2 つが要る。

## 1. 型のある図 — 辺・口・ペイロードの種類

### 1.1 3 つの種類（利用者）

| 種類 | 流れるもの | 形式の例 |
|---|---|---|
| `bdf` | `.bdf` の文書 | bdf |
| `data` | 構造を持つデータ | json・yaml・csv（tsv）・xlsx・parquet |
| `any` | 何でも（上の 2 つも、それ以外の生のファイルも） | pdf・画像・Office・zip・テキスト… |

`bdf ⊂ any`、`data ⊂ any`、`bdf` と `data` は交わらない。`any` の口は何でも受け、`bdf` の口は `bdf` だけ、`data` の口は `data` だけを受ける。

### 1.2 種類はどこに持たせるか（Claude の暫定）

辺そのものに種類を書かせるのでなく、**ノードの口（入力・出力）が種類を宣言し、辺の種類はつないだ 2 つの口から決まる**形を推す。利用者の「エッジやその接合部に種類」は、この「接合部＝口」の種類で表せる。

- 出力の口の種類が固定のノード：入口（フラグで決まる）、テンプレート変換（`bdf`）、コンバート（`bdf`）、描画（`any`。§3.3）。
- 入力の口の種類が固定のノード：printer（`bdf`）、外部 CUPS への送り（`bdf`）、display（`bdf`）、テンプレート変換（`data`）。
- **多相**（入力の種類がそのまま出力になる）：queue・class・filter（branch）・inbox・archive（入力は `any`）・sink・SMTP・FTP・S3 の出力。利用者の「入力のデータ種によって出力のデータ種も変わる」はこれ。

多相の口の実際の種類は、上流からの**推論**で決まる：入口の出力の種類から辺を下り、ノードごとに「届きうる種類の集合」を求める（図は既に閉路なしなので 1 回の走査で済む）。固定の入力の口に合わない種類が届きうるなら **PUT で断る**（今の「存在・重なり・閉路」に「型」の確かめが加わる）。例：convert=off のエンドポイントから queue を経て printer に至る辺は 400（間にコンバートのノードが要る）。

PUT の確かめに加えて、**実行時にも確かめる**：編集の途中で型が変わった図に途中まで来ていたジョブが、合わない口に届いたら、そのノードに `error` の足跡（理由「kind data is not taken by printer」）を残して止める。静的な確かめは「新しく作る図が正しい」、実行時の確かめは「流れている最中に変わっても壊れない」の役。

### 1.3 `data` の中の形（問い）

JSON・YAML は木、CSV・XLSX・Parquet は表。テンプレートの差し込み（`form.Fill`）は `map[string]any` の木を取り、表は `form.LoadData` が「名前の付いた行の列」として木に写す。種類を 3 つに保ち、形（`record` か `table` か）はペイロードの**属性**（読み手が付ける）として持ち、口の種類にはしないのを暫定とする。JSON Schema（form-m4 の bdft に焼き込んだもの）で口を縛る「スキーマ付きの data」は後の発展（§6）。

### 1.4 キャンバス

口の色を種類で分ける（Blueprint のピンの色と同じ考え）。多相の口は推論した種類の色、`any` は灰色、型の合わない辺は赤く描いて PUT の理由を出す。パレットは「入口・経路・変換・出口」に分ける（種類が増えるので）。

## 2. ペイロードとメタデータ — ジョブの中身を広げる

### 2.1 ペイロードの版（Claude の暫定。要の変更）

今はジョブに文書が 1 つ（`job-documents` の Blob、`Live` で守る）。変換のノードが入ると、**1 つのジョブに複数のペイロード**ができる（受けたままの PDF、コンバートした `.bdf`、描画した PDF …）。暫定の形：

- **Payload**：ジョブの中の 1 つの中身。`kind`（bdf / data / any）、`format`（pdf・csv …）、`size`、`sha256`、`pages`（bdf のとき）、作ったノード（足跡の番地）。Blob の ID は `<ジョブ>.<足跡の番地>`（同じ段を再試行しても同じ ID → 2 度書かない。保管の鍵と同じ考え）。
- **Leg** に「受けたペイロード」と「作ったペイロード」を持たせる。これが ETL の**系譜**（lineage）になり、保管の記録にも写せる（どの変換を経て何が残ったか。電帳法の控えの「訂正・削除の履歴」とは別だが、出所の説明になる）。
- `Live` はペイロードごとに数える。要らなくなったペイロードから消す。

「受けたままの入力も残すか」（`requirement:print-manager` の `keep-source`）は、この形では**図の問題**になる：convert=off の入口から queue で 2 つに分け、片方を archive（any）、片方をコンバート → printer にすれば原本と刷ったものの両方が残る。設定でなく図で表せるのがこの構想の利点。

### 2.2 メタデータ（利用者）

ジョブに `meta`（文字列の鍵と JSON の値の対応）を足す。使い道はテンプレートの選択、branch の規則、出口の宛先（メールの件名・FTP のパス）の差し込み。

- **出所**：API の本文（`meta` の項目）・HTTP のヘッダ、IPP の属性（job-name・requesting-user-name・media など。今の `Name`・`ClaimedUser` はここに畳める）、ファイル名、SMTP のヘッダ（From・Subject）、S3 のキーとタグ、FTP のパス、テンプレートの項目（form-m4 の「検索項目への写し」= 保管庫の検索項目。`form-archive-fields` の答えになる）、**抽出のノード**（§3.4）。
- **信用**：送り手が付けたメタデータは「名乗り」（`ClaimedUser` と同じ）。経路の選択とテンプレートの選択には使ってよいが、**権限と見える範囲の根拠にはしない**（既存の制約の延長）。Manager が確かめたもの（`SubmittedBy`、受けた入口、時刻）は別の名前の空間（`$` の接頭辞など）で、送り手は上書きできない。
- **大きさ**：ジョブの記録は yuruidb の 256 KiB に収まる要がある。鍵の数と全体の大きさに上限（暫定 64 個・16 KiB）。
- **監査と個人情報**：メタデータは監査ログと保管の記録に写るので、ここに個人情報を入れる運用は設計者が決める（Manager は検閲しない）。

## 3. ノードの種類の足し算

### 3.1 入口のフラグ（利用者）

| 入口 | フラグ | 出力の種類 |
|---|---|---|
| endpoint（REST） | `convert: on`（既定。今の振る舞い） | bdf |
| | `convert: off` | any（受けたまま。形式は見分けて `format` に） |
| | `accept: data`（データだけ） | data（data 以外は 415） |
| | `accept: template`（今のまま） | bdf（§3.2 の問い） |
| cups（IPP） | `convert: on` / `off` | bdf / any |

`formats`（受ける形式の一覧）はそのまま効く。convert=on の変換は今と同じく入口で同期に行う（既存の振る舞いを保つ）。S3・FTP・SMTP の入口（§4）も同じフラグを持つ。

### 3.2 テンプレート変換ノード（data → bdf）

テンプレート（bdft・Excel・Word・PowerPoint・PDF フォーム・pdfme・テキスト。`form.Fill` が受けるもの）を持ち、届いた data を差し込んで `.bdf` を出す。どのテンプレートを使うかは **固定**（ノードの設定）か **メタデータの鍵**（`template_from: meta.doc_type` のように、値をテンプレートの id に）か。無い id は `error` の足跡。

→ 2026-10-21 利用者の答え（§9）：テンプレートはテンプレート変換ノードに移し、エンドポイントは暗黙の変換をしない（省略形も無し）。

問い（答え済み）：テンプレートの持ち主。pm-5 で利用者は「テンプレートはエンドポイントの持ち物」を選んだが、この構想では「データはテンプレート変換ノードを使って BDF にする」とあり、テンプレートはノードの持ち物になるのが自然。A：テンプレート変換ノードの持ち物に移し、エンドポイントの `accept: template` は「data の入口 + 暗黙のテンプレート変換」の省略形として当面残す（推奨。図で見える）。B：エンドポイントの持ち物のまま、テンプレート変換ノードは上流のエンドポイントのテンプレートを引く（図の意味が歪む）。

CSV の 1 行ごとに 1 文書（宛名の差し込みのような）は、テンプレート変換の設定（`per: row`）か、別の split ノード（§6）か。暫定でテンプレート変換の設定にはせず、split に任せる（1 → N のジョブは経路の問題なので）。

### 3.3 コンバート（any → bdf）と描画（bdf → any）

- **コンバート**：届いた any を変換器で `.bdf` に（入口の convert=on と同じ変換器。`formats` で受ける形式を絞れる。解像度の上限は `converter` の既定）。data も変換できる：CSV・XLSX・Parquet は表の文書になる（変換器がある）。JSON・YAML には変換器が無い（整形したテキストにするか、断るか。暫定：断る。テンプレート変換を使う）。
- **描画**（利用者の一覧に無い。Claude が足した）：`.bdf` を PDF（`vector/pdfbdf`）・PNG・SVG にする。**SMTP や FTP の出口で `.bdf` を送っても相手は開けない**ので、メールに PDF を付けるにはこれが要る。出力の種類は any。

### 3.4 抽出（any/data → 同じ種類 + メタデータ）

ペイロードを読んでメタデータに鍵を足す：JSON・YAML の道（`$.order.customer`）、CSV の最初の行の列、`.bdf` の文書の属性（ページ数・テンプレートの項目・タイトル）、PDF の文書情報。ペイロードは変えない。branch の規則が「中身」を見たいときは、この抽出を前に置く（branch はメタデータだけを見る。経路のノードを軽く保つ）。

### 3.5 branch（filter の拡張）

pm-4b の filter が既に「規則ごとの `to` と `otherwise`」を持つので、**branch は filter を広げたもの**：規則の照合に `meta.<鍵>` の RE2 と数の比較（`min`・`max`）、ペイロードの `kind`・`format`・`pages`・`size` を加える。出力の口は規則ごとに 1 つ + otherwise。多相（入力の種類がそのまま出る）。

問い：名前。`filter` のままか、`branch` に改めるか（`printer` の `route: branch`（拠点の printd）と語が重なる）。暫定で `filter` のまま、画面の見出しだけ "Branch"。式の言語は RE2 の表（線形時間、依存なし）のままにし、CEL・expr のような式言語は要る場面が出るまで入れない。

### 3.6 プリンタと外部 CUPS（利用者：入力は bdf だけ）

printer は今のまま（入力 bdf）。**外部の CUPS サーバーへ送る出口**は、`printer` の `url` が `ipp://cups-host/printers/<名前>` を指せるので、既に表せる（CUPS のキューは IPP のプリンタ）。別の種類にする利点は「CUPS の一覧から宛先を選べる」「クラスも宛先にできる」くらい。暫定で printer のまま、サイドバーに「CUPS の一覧から選ぶ」を足す。

### 3.7 archive・sink・inbox（多相）

archive は any を受け、受けたペイロードをそのまま書く（`.bdf` でなくてもよい。記録の JSON に `kind`・`format` と系譜）。sink は `.bdf` ならサムネイル、それ以外は名前と大きさ。inbox は何でも持つ（人が見て流す）。

## 4. 入出力のノード（利用者：SMTP・FTP(S)・S3）

### 4.1 出口

| 種類 | 設定 | 備考 |
|---|---|---|
| `smtp` | ホスト・ポート・STARTTLS/TLS・資格の**名前**・From・To（固定とメタデータの差し込み）・件名と本文のテンプレート | 添付はペイロード（`.bdf` のままでは相手が開けないので描画を前に）。再試行の 2 重送りは Message-ID を `<ジョブ>.<足跡>` にして受け手側で抑える程度 |
| `ftp` | ホスト・FTPS（明示的 TLS）か SFTP か・資格の名前・パスのテンプレート | 一時の名前に上げてから改名（部分的なファイルを見せない）。SFTP は x/crypto/ssh（既に依存）+ sftp の部品 |
| `s3` | バケット・接頭辞のテンプレート・資格の名前 | yuruidb の Blob（S3・R2・GCS）で書ける。archive との違いは「変えない約束と記録の JSON が無い、ただの置き場」 |
| `http`（利用者の一覧に無い。Claude が足した） | URL・方法・ヘッダ・資格の名前 | 外部の Web サービスへ押す。serverless の外部 Lambda と対になる |

**資格は名前で指す**（`credential: smtp-main` → 環境変数 `PM_CRED_smtp_main` かファイル）。yuruidb には置かない（`requirement:print-manager-auth` の制約「取り出して使える秘密を置かない」）。cups の `tls_cert`・`tls_key` がファイルのパスなのと同じ形。問い：根の秘密で封をして yuruidb に置く（画面で設定できる）案との比較（§7 の問い 7）。

**宛先の差し込み**（To・件名・パス・接頭辞）はメタデータから。式でなく `{meta.key}` の置き換えだけにし、パスは `..`・`/` の頭を落とす、メールのヘッダは改行を落とす（ヘッダの注入とパスの逸脱を防ぐ）。

### 4.2 入口

- **S3（イベント）**：常駐しない前提なので、Manager が待ち受けることはできない。S3 のイベント → EventBridge / SNS / Lambda → **`POST /in/<node>` にオブジェクトのキーを渡す**（本文でなく参照。pm-5c で利用者が決めた「外部の Lambda が入力ノードの ID をパスに持つ API を叩く」形そのもの）。Manager が yuruidb の Blob で読む。当初は **tick での見回り**（`ListObjects` を接頭辞と前回の続きから）を保険に考えたが、2026-10-21 利用者の答え（§9）で入口は S3 Trigger だけ、出口は書きっぱなしにした。
- **FTP**：tick での見回り（一覧 → 新しい名前を取る → 取ったものは「済み」の接頭辞へ改名か、取った名前の記録）。
- **SMTP の受け**（利用者の一覧に無い）：Manager が SMTP サーバーになるのは常駐が要るので、サーバーレスでは外部（SES の受信 → S3 → 上の S3 の入口）に任せる形。プロセスで動くときは IMAP の見回り（tick）か、小さな SMTP の受け口（ポートのノードの仲間）。
- **watch folder**（プロセスのときだけ）：ディレクトリの見回り。拠点の printd 的な使い方。

入口は全部 §3.1 のフラグ（convert / accept）を持つ。

### 4.3 送りの意味

at-least-once（今の Delivery と同じ：借り、再試行、`failed`）。**冪等の鍵は `<ジョブ>.<足跡>`**：S3 は `If-None-Match: *`、FTP は一時名 → 改名、SMTP は Message-ID、HTTP は `Idempotency-Key` ヘッダ。結果が分からない失敗（応答が来ない）は再試行で 2 度送ることがある（受け手が鍵で抑える前提。文書化）。

## 5. 変換ノードの拡張（利用者：アプリが任意に拡張）

| 案 | 形 | 向き・不向き |
|---|---|---|
| A. 組み込みの登録 | Go の `manager.Options.Transforms`（名前 → 関数）。bdf をライブラリとして使う人が自分のバイナリで足す | サーバーレスでも動く。Go だけ。配布の単位がバイナリ |
| B. HTTP の押し出し | transform ノードが**アプリの URL に POST**（ペイロード + メタデータ、`multipart` か JSON）し、応答のペイロード（と meta の差分）を次へ | 言語を問わない。Lambda の Function URL と相性がよい。アプリが Manager からの呼び出しを確かめる手段（HMAC の署名か、アプリの資格を Manager が持つ）が要る。同期なので長い処理は時間切れ |
| C. HTTP の引き取り | transform ノードがジョブを持ち（inbox と同じ）、**アプリが `GET /api/nodes/<n>/work` で取り、`POST …/work/<id>` で結果を返す** | アプリへの到達性が要らない（オンプレの基幹から取りに来られる）。長い処理に向く。pm-auth-2 のアプリの資格（client credentials）がそのまま使える |
| D. Wasm | ノードに Wasm のモジュールを上げ、wazero（純 Go）で走らせる | 砂場つき、サーバーレスでも動く、言語を問わない。実行系の依存が大きい。ペイロードの受け渡しの ABI を決める要がある |

→ 2026-10-21 利用者の答え（§9）：B の押し出しで、相手は登録した外部のマイクロサービス。

当初の推奨：**A（組み込み）を土台に、B と C の両方を 1 つの `transform` ノードの `mode` にする**（`mode: http` は押し出し、`mode: pull` は引き取り）。どちらも契約は同じ：入力（ペイロード・kind・format・meta）→ 出力（ペイロード 0 個か 1 個か複数、meta の差分、または失敗の理由）。ノードの設定で**入力と出力の種類を宣言**し（アプリの manifest）、型の推論に乗せる。D は後の発展。

拡張の契約で決めること：ペイロードの大きさの上限と時間切れ、再試行してよいか（冪等か）の宣言、出力が複数のときの扱い（split と同じ）、失敗（4xx は `error` の足跡で止める、5xx と時間切れは再試行）、契約の版。

## 6. 他に考えられる発展（Claude の案）

ETL の定番のうち、利用者の一覧に無いもの。入れる・入れないの判断は利用者。

1. **描画ノード**（bdf → PDF/PNG/SVG。§3.3）— メールと FTP の出口に実質必須。
2. **split**（1 → N）：CSV の行ごと、Parquet の行の群、zip の中のファイル、`.bdf` のページの範囲。ジョブを N 個に分ける（親子の系譜）。
3. **batch / merge**（N → 1）：時間の窓か件数で集め、`.bdf` のページを連結（1 日分の伝票を 1 つの PDF に）、CSV の行を連結。常駐しない前提なので「窓の閉じ」は tick で見る。
4. **schedule の入口**：cron の時刻に空のジョブ（メタデータだけ）を作る。S3 から日次のレポートを作る流れの起点。tick の仕組みで作れる。
5. **dedupe**：`sha256` かメタデータの鍵で 2 度目を捨てる（再送の多い FTP と S3 の入口の後ろに）。
6. **on_error の口**：どのノードにも任意の `on_error` の辺（多相。入力のペイロード + 失敗の理由を meta に）。無ければ今の `failed`/`aborted`。全体の dead-letter はこれを 1 つの inbox に集めるだけで作れる。
7. **人の入力の入口**（form）：画面で利用者がテンプレートの項目を打って data のジョブを作る（Print Manager の /jobs に「作る」）。form-m4 の JSON Schema から画面が作れる。
8. **スキーマ付きの data**：口に JSON Schema を宣言し、テンプレートの項目（`tag.Field`）と突き合わせて PUT で確かめる（§1.3）。
9. **文書側の変換の族**：スタンプ（日付・「控」・QR）、透かし、面付け（2 アップ・小冊子）、ページの選択・回転、領域の黒塗り。今の `.bdf` の操作で作れるものが多い。
10. **データ側の変換**：列の選択・改名、行の絞り込み、表の結合、集計、JSON ↔ CSV ↔ Parquet の書き出し。ここは際限が無いので、組み込みは「形式の変換（読み手はある。Parquet と XLSX の**書き手は無い**）と抽出」までにし、残りはアプリの拡張（§5）に任せるのを推す。
11. **join**（相関の鍵で 2 つの入力を待つ）：常駐しない前提で「待つ」のが重い（inbox 的な持ち方 + tick）。後。
12. **ノードごとの流量の制限**（同時 1 件のプリンタ、SMTP の毎分の上限）と**バックプレッシャー**：ETL では印刷より量が増える。宛先ごとの一覧の上限 500、yuruidb の一覧の性能、tick の 1 回の件数を見直す。
13. **トポロジーの版と下書き**（`requirement:print-manager-console` の `node-edit-live`、non_goals の版の管理）：型のある図を流れている最中に直すなら、この問いが前に出る。
14. **複数のトポロジー**（用途ごとのキャンバス）：名前の空間 1 つのままでは ETL の流れと印刷の流れが同じ絵に混ざる。フォルダか接頭辞の表示だけでも。
15. **製品の名前**：Print Manager の名が合わなくなる（README は既に "software-defined document network"）。

## 7. 考慮すべきこと（まとめ）

1. **型検査を PUT に足す**（§1.2）：存在・重なり・閉路に「型」。推論は上流から 1 回の走査。実行時の確かめも残す。
2. **ジョブの中身を「文書 1 つ」から「ペイロードの列 + メタデータ」に**（§2）：Blob の ID・`Live`・保管の記録・`/api/jobs` の形が変わる。既存の `.bdf` だけの図は「ペイロード 1 つ」の特別な場合として互換を保つ。
3. **変換はノードの段（Delivery の一般化）**：経路のノードは即座、変換と出口は借りの下の非同期の段。`deliver.go` が「段の実行」に広がり、種類ごとの実行器を持つ。サーバーレスでは tick の 1 回の時間で終わる大きさに（大きな変換は分ける・断る）。
4. **メタデータは名乗り**（§2.2）：権限の根拠にしない。確かめた値は別の名前の空間。大きさの上限。
5. **秘密は名前で指す**（§4.1）：出口の資格を yuruidb に置かない。差し込みはヘッダの注入とパスの逸脱を防ぐ。
6. **冪等の鍵と at-least-once**（§4.3）：`<ジョブ>.<足跡>`。
7. **大きさ**：Lambda の同期呼び出しの本文は 6 MB（記憶）。Parquet・Excel は大きくなりうる。`MaxDocument` と presign の受け取り（popcornweb の storage）を data にも。流しながらの変換。
8. **互換**：既定（convert=on、辺は bdf、テンプレートはエンドポイント）で今の図がそのまま動く。移行は型の推論で自動（全部 bdf）。
9. **失敗の行き先**（§6 の 6）：ETL では「落ちたものをどこで拾うか」が運用の中心。
10. **試験の偽物**：偽プリンタの農場と同じく、偽の SMTP（プロセス内）、偽の FTP、S3 の偽物（yuruidb の確かめ用か rustfs）。型検査は図の性質のテスト（閉路 + 型を乱数の図で）。
11. **依存**：SMTP は `net/smtp`（標準）、FTPS と SFTP は外部の部品、式言語と Wasm は入れない（当面）。
12. **範囲の歯止め**：「汎用 ETL」は際限が無い。組み込みは文書の変換・形式の変換・抽出・テンプレート・経路・入出力までにし、データの加工はアプリに任せる（§6 の 10）。

## 10. fl-1 の実装（2026-10-22）

`milestone:fl-1`。利用者「fl-1 の実装を始めてください。暫定の既定はそのままで」。

- **型**：`kinds.go`。口の種類は `takes(kind)`（printer・display は bdf、template は data、他は全部）と `Node.emits(in)`（入口は `in | entryKind`、template・convert・display は bdf、他は `in`）。`inferKinds` が入口から不動点まで辿り、`typed` が PUT のたびに全ノードを確かめる（理由に「raw → fan → laser」の道）。`/api/topology` に `takes` と `emits`。実行時は `route` の先頭で `takes(kind).has(payload.Kind)`。
- **ペイロード**：`Job.Payloads`（受けたものの ID はジョブの ID のまま、作ったものは Delivery の ID `<ジョブ>.<足跡>`）、`Leg.Payload`・`Leg.Made`、Slip・Item・Delivery に `Payload`。Live はジョブごとのまま（ペイロードはジョブと一緒に消す）。
- **メタデータ**：`meta.go`。送り手（`X-Meta-*`、`?meta.*`、IPP の job attributes を `ipp.<名>`）< 入口の `meta` < `$` の鍵。規則とテンプレートは `metaView`（文字の表 + `name`・`user` + ペイロードの `$kind` …）を見る。ヘッダの鍵は小文字（`Doc-Type` → `doc-type`）。
- **入口**：`accept: file | data`、`output: bdf | file`（data のときは空）、`formats`、`meta`。テンプレートの差し込みと JSON の封筒は無くなった。`cups` も同じ欄。
- **変換の段**：`transform.go`。Delivery の `Kind` が template・convert のとき `transform` → `outcome`（done）→ `continueWith`（ペイロードを足し、`to` へ route、kick）。最終の失敗（`finalErr`）は再試行しない。
- **分かったこと**：CSV・Parquet の表の文書（`xlsx.ConvertGrid`）にはページのビューが無く、印刷（`print.PrintView`）で止まる。入口の convert でも convert ノードでも同じ。変換器の側の宿題（grid の印刷ビュー）。
- **未確認**：ブラウザの画面、S3・R2・GCS、Lambda。

## 11. fl-1b：型で色の付くエディタ（2026-10-22）

`milestone:fl-1b`。利用者「GUI ツールはかなりよくなったが、UE5 みたいに、トポロジーのエッジを流れるデータ種でノードの色を変えて接続の可否が分かりやすくして欲しい。分岐のようなやつは最初に繋がれたもので出口も変わるように。設定を変えて繋がらなくなったものは破線などになると良い」。

- **サーバー**：`/api/topology` に `accepts`（今そのノードに送れる種類。自分の `takes` と、後ろの全ノードの `accepts` の共通部分。printer の前の queue は bdf だけ、printer と template の前の queue は空）と `broken`（送り先が受けない種類を運ぶ辺。`{"laser": ["any"]}`）。`typed` は **新しい辺**（そのノードが持っていなかった辺）で合わない種類が届くようになる PUT だけを 400 にし、設定の変更（入口の `accept`・`output`、種類の変更）で既にある辺が合わなくなるのは通して `broken` に出す。壊れた辺を通ったジョブは fl-1 のまま `route` の実行時の確かめで `error` の足跡。
- **キャンバス**：口・辺・ノードの枠を種類の色に（bdf 青、data 緑、any 琥珀、複数は紫）。通過ノード（queue・class・filter・inbox）は届く種類か、無ければ後ろの `accepts` で型が決まる（最初の辺が入口側でも出口側でも）。どちらも無ければ中空の破線（未定）、何も合わなければ赤。convert・archive・sink の入力は濃い灰（どれでも受ける）。辺をドラッグすると、受けない先（自分・cups・display は printer 以外・重複・閉路・種類が合わない）が薄くなり、線がその上で赤くなって理由のラベルが出る。受ける先では口に吸い付く。落としたときも断ってトースト（サーバーでも同じ確かめ）。壊れた辺は赤の破線と「!」の印。凡例を両ページに。
- **サイドバー**：送り先の選択に種類の点と「would not take it」、`accepts` と壊れた辺の説明、保存で辺が壊れたらトースト。
- **決めたこと**：`any` の色は灰から琥珀に（未定の灰と見分ける。`admin.js` の 1 行）。class の member の辺は破線をやめ中空の矢印に（破線は壊れた辺の印）。
