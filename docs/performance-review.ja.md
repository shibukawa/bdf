# 通常処理のパフォーマンス改善

測定日: 2026-10-06。前回の入力制限に続き、正常な文書を扱う際の処理時間とメモリ確保量を測定した。

## 変更

- BDF の圧縮器を圧縮レベルごとに再利用する。部品ごとに大きな作業領域を新規確保していた処理を減らした。出力バッファは再利用せず、以前返したバイト列の内容を保つ。
- BDF の展開器も再利用する。返却時に入力への参照を切り、次の使用時に辞書とエラー状態を初期化する。展開サイズの上限は引き続き検査する。
- ページ・シート・スクロール表示の背景が整数境界の矩形なら、画素ごとのシェーダー・被覆率・クリップの検査を省く。小さいパスの描画に追加コストが入らないよう、背景専用の処理にした。半透明の背景も同じ source-over の演算を行い、端に部分的な被覆がある場合は通常の描画を使う。

圧縮・展開の作業領域は `sync.Pool` に預けるため、GC で回収されることがある。文書の入力バイト列や返却した出力バイト列をプールに保持しない。

## 測定方法

Apple M3、macOS、Go 1.27.0、darwin/arm64。修正前と修正後のテスト実行ファイルを分け、リポジトリ内の同じ文書を使用した。

`BenchmarkDocumentIO` は、読み込みを `Reader.ToDocument()`、保存を `Document.WriteSingle(io.Discard)` で測る。ディスク I/O と manifest の初回読み込みは含まない。同一プロセスでの繰り返し処理を 500 ms × 3 回測定し、中央値を比較した。メモリは Go の `B/op`（処理ごとの確保量）であり、プロセスの常駐メモリではない。

| 文書 | 処理 | 修正前 | 修正後 | 時間の短縮 | メモリ確保量の変化 |
|---|---|---:|---:|---:|---:|
| PDF `chrome-doc` | 読み込み | 78.1 µs | 71.5 µs | 8% | 174 KB → 53 KB |
| draw.io `showcase` | 読み込み | 40.4 µs | 35.3 µs | 13% | 99 KB → 18 KB |
| EPUB `basic` | 読み込み | 98.1 µs | 83.9 µs | 14% | 282 KB → 39 KB |
| PDF `chrome-doc` | 保存 | 453 µs | 294 µs | 35% | 4.60 MB → 21 KB |
| draw.io `showcase` | 保存 | 289 µs | 176 µs | 39% | 3.44 MB → 14 KB |
| EPUB `basic` | 保存 | 656 µs | 378 µs | 42% | 8.05 MB → 59 KB |

`BenchmarkRenderPage` は同じ Renderer を使い、初回の資源読み込み後のページ描画と RGBA 画像の作成を測る。通常ページは scale=1、サムネイルは scale=0.25。システムフォントを使わず、リポジトリのテスト用フォントを指定する。描画は `GOMAXPROCS=1` とし、修正前・修正後を交互に 750 ms × 3 回測定する。

| 文書 | 描画サイズ | 修正前 | 修正後 | 時間の短縮 |
|---|---|---:|---:|---:|
| PDF `chrome-doc` | 通常ページ | 19.92 ms | 17.93 ms | 10% |
| PowerPoint `features` | 通常ページ | 10.46 ms | 8.73 ms | 17% |
| draw.io `showcase` | 通常ページ | 2.90 ms | 2.89 ms | ほぼ同等 |
| PDF `chrome-doc` | サムネイル | 5.54 ms | 5.19 ms | 6% |
| PowerPoint `features` | サムネイル | 1.24 ms | 1.12 ms | 10% |
| draw.io `showcase` | サムネイル | 0.840 ms | 0.835 ms | ほぼ同等 |

背景が占める画素数の多いページで効果が大きい。数%の差は測定時の負荷でも変動するため、小さい描画すべてが速くなるという結果ではない。読み書き・描画とも、初回のフォント探索、入力形式からの変換、ディスクやネットワーク待ちは別のコストになる。

再測定のコマンド:

```sh
go test -run '^$' -bench BenchmarkDocumentIO -benchmem -benchtime 500ms -count 3 .
go test -run '^$' -bench BenchmarkRenderPage -benchmem -benchtime 750ms -count 3 -cpu 1 ./raster/imagebdf
```

## 検証

- `go test ./...` と `go vet -unreachable=false ./...` が成功。
- 既存の全テスト文書を使う `TestShortcutsChangeNoPixel` で、最適化を有効・無効にした描画がバイト単位で一致。Chromium の golden 画像との既存の比較も成功。
- 背景の色・透明度・整数境界・部分的な被覆を変えて、専用処理と通常の描画の浮動小数点値が一致することを確認。
- 全圧縮レベルで、空・小・大・圧縮しにくい入力を続けて処理し、新規作成した圧縮器との出力バイト一致を確認。前の出力を後続の圧縮が変更しないことも検査。
- 壊れた deflate や展開上限を超えた入力の後でも、正常なデータを展開できる。
- 圧縮・展開の並列利用と変更した描画経路のテストを race 検査付きで実行して成功。
- TinyGo 0.42 の HTML/PDF WASM ビルドに成功。Chrome 上で PDF → HTML → PDF を連続変換し、18 個の BDF 部品の展開と、最初・最後の PDF の出力バイト一致を確認。
- 最終的な背景描画の変更を含め、通常の Go でも `bdf_noconv,pdfonly` の WASM ビルドに成功。
- PR 作成時に最新 main の `raster/imagebdf` への移動を取り込み、Go 全体・vet・Ebitengine サブモジュール・npm 132 件のテストを再実行して成功。上記の実測は移動前のパッケージで行い、再測定コマンドは移動後のパスに更新した。
