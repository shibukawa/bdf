# インボックスと配送 {#inboxes-and-deliveries}

2 つのページは、途中にあるジョブのためのものです。人が手でジョブを送り出す「インボックス」（アプリケーションは API で同じことをします）と、マネージャーが自分で送るものを見守り、再試行する管理者の「配送」です。

## インボックス {#inboxes}

インボックスは、到達したすべてのジョブを、誰かが送り出すか破棄するまで留めるノードです。手で動かすフィルタです。印刷前の承認や、1 日の終わりにまとめて送るのに使います。インボックスのページ（`/inboxes`。インボックスを扱う人のバーと、管理のタブにあります）には、自分が扱うすべてのインボックスと、留まっている項目が古い順に、それぞれ 1 ページ目のサムネイル付きで並びます。

- **送り出す** は、項目をノードへ送ります。インボックスの `to` のノード（既定で全部にチェック）、またはインボックスが指定していなければ、欄に入れたコンマ区切りの名前です（名前を入れられるのは役割 topology だけです）。
- **破棄** は項目を終わらせます。ジョブはここから先へは送られません。
- **作業者** の名前は、誰が送り出し、破棄したかとして、記録と監査ログに書かれます。空なら自分の名前です。
- サムネイルからは、項目が留めている文書をダウンロードできます。

送り出した項目と破棄した項目は、一覧の下にインボックスの保持期間（`keep`、既定 14 日）の間表示され、どこへ行ったか、誰が送ったかが分かります。「ノードを編集」はトポロジーでインボックスを開きます。ジョブのページで取り消したジョブはインボックスから消えます。

## インボックスを扱う人 {#workers}

| 誰が | 扱うもの |
|---|---|
| 役割 topology（管理者、管理トークン、スコープ `admin` のアプリ） | すべてのインボックス。送り出し先を挙げていないインボックスからは、どのノードへも送り出せます |
| インボックスのスコープの人 | `group` のインボックスならそのメンバー、`personal` のものなら所有者。`shared` のインボックスにはいません。扱うのは役割 topology です |
| インボックスが挙げたアプリ（許可するアプリ）で、スコープ `inbox` を持つもの | そのインボックスを、自分のトークンで |
| フロントエンドが受け取った人のトークン（スコープ `inbox` の公開クライアント） | その人が扱うインボックス |

役割 topology 以外が送り出せるのは、インボックスの `to` だけです。ノードを 1 つも挙げていないインボックスは、役割 topology が指定した先へ送り出します。扱えないインボックスは、理由を添えて拒否されます（403）。

## インボックスの API {#api}

ページでできることは、そのまま API になっています。文書の承認を自分で行うアプリケーション（ワークフローシステム、上長が承認するポータル）向けです。

| | |
|---|---|
| `GET /api/inbox` | 呼び手が扱うインボックス。`name`、`title`、`description`、`to`（送り出せるノード）、`held`（項目の数）、`rev` |
| `GET /api/inbox/<name>` | インボックス。`held` は留まっている項目（古い順）、`ended` はまだ表示されている送り出し・破棄した項目（新しい順）、そして `to` です。`If-None-Match` に前の応答の ETag を付ければ、何も変わっていない間は 304 です |
| `GET /api/inbox/<name>/<job>` | ジョブの番号で指す項目。送った人、名前、ページ、状態 |
| `GET /api/inbox/<name>/<job>/thumbnail?size=&mode=` | 1 ページ目の PNG。ページ全体を長辺 `size` ピクセル（256。32 から 1024）で、`mode=crop` なら上端の正方形 |
| `GET /api/inbox/<name>/<job>/pages/<p>.png?w=` | ページを幅 `w` ピクセル（800）で |
| `GET /api/inbox/<name>/<job>/document` | 留めている文書を、留めているままの形で。ダウンロードのたびに監査ログに残ります |
| `POST /api/inbox/<name>/<job>/release` | `{"to": ["<node>", …], "worker": "…"}`。先へ送り出します。`to` がなければ、インボックスが送り出せるすべてのノードへ。もう留まっていなければ 409 |
| `POST /api/inbox/<name>/<job>/discard` | `{"worker": "…"}`。項目を終わらせます |

サムネイルとページは `.bdf` 文書のものです。受け取ったままのファイル（`output: file` のアップローダー）やデータの項目にはなく（404）、文書だけがあります。OpenAPI 文書は、送り出せるノードとともにインボックスの API を記述します（[OpenAPI](api.md#openapi)）。

```sh
TOKEN=$(curl -s -u 'approvals:<secret>' -d grant_type=client_credentials https://<host>/oauth/token | jq -r .access_token)
curl -H "Authorization: Bearer $TOKEN" https://<host>/api/inbox/review
curl -H "Authorization: Bearer $TOKEN" -o 12.png "https://<host>/api/inbox/review/12/thumbnail?size=256"
curl -X POST -H "Authorization: Bearer $TOKEN" -d '{"to": ["laser"], "worker": "Sato"}' https://<host>/api/inbox/review/12/release
```

## 配送 {#deliveries}

配送は、マネージャーが自分で送るものです。プリンタやアーカイブへのジョブと、テンプレートノードや変換ノードのステップです。ジョブの経路が決まったときに作られ、その直後にプロセスが、またはティックが行います。管理 → 配送には、待っている配送と失敗した配送が並びます。ジョブ、ノード、プリンタ（クラスなら試したメンバー）、状態、試行回数、次の試行の時刻、最後のエラーです。

- 失敗した配送（届かないプリンタ、応答しないストア）は、だんだん長くなる間隔で再試行されます。30 秒、次に 1 分、2 分、4 分、8 分、その後は 15 分ごとに、最大 20 回、およそ 4 時間です。クラスは次のメンバーを試します。最後の試行の後、配送は最終的に失敗し、ジョブは `aborted` になります。
- 再試行では直らない失敗（テンプレートがない、データが読めない、コンバータのない形式）は、すぐに最終的な失敗になります。
- **今すぐ再試行** は、配送をすぐに送り直します。時刻を待っているものも、最終的に失敗したものもです。

## ティック {#tick}

ティックはやるべきことを行います。待っている配送と再試行する配送を送り、誰も時間内に開かなかった伝票（と、デバイスが 1 台もつながっていないディスプレイの未開封の伝票すべて）を紙に印刷し、ディスプレイやインボックスの保持期間より前に終わった伝票と項目、終わって何も表示していないジョブ、期限切れの登録コードを削除します。プロセスは 30 秒ごとにティックします（運用者の `tick_interval`）。サーバーレスでは、スケジューラが毎分 `POST /api/tick` を呼びます（[サーバーレス](operate.md#serverless)）。管理 → 配送の **今すぐティック** はティックを実行し、何をしたかを報告します。
