# 流れるもの {#what-flows}

ジョブがエッジに沿って運ぶものと、ともに流れるもの。ペイロードとその種類、メタデータ、そしてそれらを見るフィルタのルールです。

## ペイロードの種類 {#kinds}

エッジを流れるものは 3 種類のどれかです。

| 種類 | | 色 |
|---|---|---|
| `bdf` | `.bdf` 文書。プリンタ、ディスプレイ、ページが表示するもの | 青 |
| `data` | テンプレートのためのデータ。JSON、YAML、CSV、Excel ブック、Parquet ファイル | 緑 |
| `any` | 受け取ったままのそれ以外のファイル（PDF、Office 文書、画像）。変換ノードやアーカイブ向け | 琥珀色 |

ノードが送り出すもの:

- 入口（エンドポイント、CUPS サーバー）は設定どおりのものを送ります。`accept: data` ならデータ、`output: file` なら受け取ったままのファイル、それ以外は文書から作った `.bdf`（既定）です。
- テンプレートノードと変換ノードは、作った `.bdf` を送ります。`original` には到達したものをそのまま送ります。
- ディスプレイはフォールバックプリンタが印刷するもの、`.bdf` を送ります。
- それ以外のノードは到達したものをそのまま送ります。

ノードが受け取るもの: プリンタとディスプレイは `bdf` だけ、テンプレートノードは `data` だけ、それ以外のノードは何でも受け取ります。いまノードに送れるものはもっと狭く、受け取るもののうち、その先のすべてのノードが受け取るものです。プリンタの前のキューは `.bdf` だけを受け取ります。プリンタが印刷できるものしか運ばないからです。まだエッジのないキュー、クラス、フィルタ、インボックスは、どちら側でも最初のエッジの種類を受け取ります。キャンバスはポートとエッジをこれらの種類で色分けします。青は `bdf`、緑は `data`、琥珀色は `any`、紫は複数です。まだ型の決まっていないポートは中抜きの破線です。

ノードを保存するとき、各ノードに到達する種類を入口からエッジに沿って推定します。受け取れない種類をノードに持ち込む新しいエッジは拒否されます。メッセージは経路を示します。「laser (printer) takes bdf, but any reaches it: raw → fan → laser」です。`GET /api/topology` は各ノードの `takes`、`emits`、`accepts`（いま送れるもの）、`broken` を示します。

## 壊れたエッジ {#broken}

ノードの設定だけを変えたとき（入口がデータを受け取るようになった、キューをテンプレートノードにした）は、先のノードが受け取らないものを運ぶエッジが残っても保存されます。エッジは壊れたまま残ります。キャンバスは赤い破線に印を付けて描き、エッジが出るノードのサイドバーが理由を示し、保存のときにどのエッジが壊れたかを知らせます。直すには、間に変換ノードかテンプレートノードを置く、設定を戻す、エッジを外す、のどれかです。

ジョブのペイロードは到達する各ノードで再び検査されます。壊れたエッジがあっても、ジョブが流れている間にトポロジーが変わっても、ジョブは壊れません。ペイロードを受け取れないノードでは、レグが `error` になります。

## ペイロード {#payloads}

ジョブはペイロードを運びます。受け取ったもの（`kind`、`format`、`pages`、`size`、`sha256`、送り手がファイル名を与えていれば `name`）と、テンプレートノードや変換ノードがそれから作ったものです。作ったものにはどのノードが作ったかが記されます。各レグには、ノードが受け取ったペイロードと作ったペイロードが記されます。ジョブの文書（Jobs ページ、ディスプレイの伝票、プリンタで扱うもの）は、最後に作られた `.bdf`、なければ受け取ったものです。`GET /api/jobs/<n>/document` でダウンロードでき、`?payload=<id>` でほかのペイロードも取れます。

形式はコンバータの名前（`bdf`、`pdf`、`docx`、`xlsx`、`pptx`、`image` ……）と、データの `json`、`yaml`、`csv`、`xlsx`、`parquet` です。`GET /api/formats` が入口の受け取れる形式を一覧します。送られたものの形式は、名前かコンテンツタイプ（JSON、YAML、CSV）、または内容から判別します。Excel のブックと CSV ファイルは、受け取ったまま送られるとき（`accept: data` か `output: file` の入口）はデータで、入口が `.bdf` にするときは文書です。

## 原本とトレース {#traces}

テンプレートノードと変換ノードは、作った `.bdf` を `to` へ、受け取ったまま（データ、受け取ったファイル）を `original` へ送ります。たとえば原本のアーカイブと、作ったもののアーカイブを並べられます。`original` のエッジはノードに到達した種類を運ぶので、受け取ったままのファイルをその経路でプリンタへ送ることはできません。キャンバスは短い破線で描きます。

両側にはそのステップの `trace` が付きます。

| | |
|---|---|
| `id` | ステップの id。両側で同じです |
| `node`、`kind` | テンプレートノードか変換ノード |
| `role` | どちら側か。`original` では `source`、`to` では `output` |
| `source`、`output` | 両方のペイロード（`payload`、`kind`、`format`、`name`、`sha256`）と、アーカイブが付ける名前 `key` と `object`（`<受け取った日>.<ジョブの id>.<sha256 の先頭>`。記録は `<key>.json`） |
| `fingerprints` | ペイロードの系譜のすべてのステップ。古い順に `id`、`node`、`role` |

アーカイブは記録に、エクスポートは項目にトレースを書きます。どちらのオブジェクトからも、相手が送られたアーカイブの中の名前が分かります。マネージャーは相手を探さず、書かれたかどうかも確かめません。トレースはキュー、フィルタ、クラス、インボックス、アーカイブを通ってペイロードとともに進み、次のテンプレートノードか変換ノードで新しくなります。新しいトレースは前の fingerprints を引き継ぐので、何ステップも離れた 2 つのオブジェクト（受け取った PDF と、そこから作った `.bdf` にスタンプした `.bdf`）は、fingerprints に共通するステップの id で突き合わせられます。両側は同じジョブなので、それぞれのアーカイブの後のエクスポートは同じジョブ番号で一覧します。

## メタデータ {#metadata}

メタデータはジョブとともにトポロジーを流れます。3 つの出どころがあり、キーごとに 1 つ、後のものが優先します。

1. **送り手のもの。** エンドポイントや API へのリクエストの `X-Meta-<Key>` ヘッダ（キーは小文字になります）と `?meta.<key>=` パラメータ、その `multipart/form-data` のボディのパート `meta` にある JSON オブジェクト（[エンドポイント](entries.md#endpoints)）、IPP リクエストのジョブ属性は `ipp.<name>`（`ipp.media`、`ipp.copies`、`ipp.job-name` ……）です。これらは申告です。管理者の設定どおりにフィルタが振り分け、テンプレートノードがテンプレートを選ぶのに使いますが、何かを許可することはありません。
2. **入口のもの。** ジョブが入ったエンドポイントや CUPS サーバーの `meta` です。
3. **マネージャーのもの。** 送り手が書けない、`$` で始まるキーです。`$job`（番号）、`$received`（日時）、`$entry`（ジョブが送られたノード）、`$source`（入った経路）、`$sender` と `$sender_kind`（確認した送り手: 人、アプリ、トークン、エンドポイント、匿名）、`$file`（ジョブの名前）です。

キーは英数字と `_`、`.`、`-`、`/` で、64 文字までです。ジョブのメタデータはキー 64 個、16 KiB までです。Jobs ページではジョブの名前にマウスを重ねるとメタデータが見え、アーカイブの記録はメタデータを保持します。

ノードでは、フィルタのルールとテンプレートノードの `template_from` は、ジョブのメタデータ、ジョブの `name` と `user`、そしてノードに到達したペイロードの `$kind`、`$format`、`$pages`、`$size`、`$sha256`、`$payload`（その id）を見ます。それが出てきた、または入っていったステップのトレース `$trace`、`$trace_role`、`$trace_node`、`$trace_peer`、`$fingerprints` も見ます（[原本とトレース](#traces)）。

### プリンタへ渡るもの {#ipp-attributes}

プリンタノードがジョブを印刷するとき、いくつかのキーは同じ名前の IPP 属性としてプリンタに渡ります。`ipp.job-account-id` と `ipp.job-accounting-user-id`（印刷を課金するアカウント。PWG 5100.7）、`ipp.document-metadata`（Dublin Core のキーか `x-` で始まるキーの `key=value` 文字列。PWG 5100.13）、`ipp.x-…`（独自の属性）です。IPP リクエスト自身の属性か、エンドポイントや API へのリクエストのメタデータ（`?meta.ipp.job-account-id=sales`）で与えます。属性が受け付けない値は渡しません。残りをどう使うかはプリンタ次第です。

## フィルタのルール {#rules}

ルールは一致条件と、一致したジョブの行き先のノードです。条件はすべて満たさなければなりません。

| 条件 | |
|---|---|
| name | ジョブの名前への正規表現（RE2） |
| user | 送り手が名乗った名前と、確認した送り手のラベルへの正規表現 |
| format | 受け取った形式への正規表現。`pdf`、`docx` …… |
| min pages、max pages | ペイロードのページ数の範囲 |
| metadata | キーごとの、値への正規表現。ジョブにないキーは一致しません |
| kind of payload | `bdf`、`data`、`any` |

ルールは順番に試され、最初に一致したものがジョブを送ります。レグにはそのルールが記されます。どのルールにも一致しないジョブはフィルタの otherwise へ行くか、なければそこで終わります（`dropped`）。条件のないルールはすべてのジョブに一致します。
