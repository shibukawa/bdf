# Go の変換・サムネイル生成のメモリと処理時間

2026-10-06、LibreOffice / Poppler と比較したベンチマークの Go 側を調査・改修した。入力文書から BDF と 256 px の先頭ページ PNG（fit）を作る処理で、起動から終了までを測っている。

修正前後を同じ日に交互に実行した結果、5 文書すべてでピークメモリと処理時間が減った。最大常駐メモリ（RSS）は 36〜61%、macOS の peak memory footprint は 36〜67%、処理時間は 14〜84% 減少した。BDF の出力サイズは 0.06〜5.1% 増える。フォント圧縮は可逆で、5 文書の PNG は修正前後でバイト単位で一致した。

## 修正前後の実測

各 5 回の中央値。メモリは MiB、時間は秒。RSS と footprint は異なる指標で、各列の中央値が同じ実行回の値とは限らない。

| 入力 | RSS: 修正前 → 修正後 | RSS 削減率 | footprint: 修正前 → 修正後 | 時間: 修正前 → 修正後 | 時間短縮率 |
|---|---:|---:|---:|---:|---:|
| `basic.docx` | 120.6 → 70.1 | 42% | 107.4 → 57.0 | 0.32 → 0.05 | 84% |
| `basic.pptx` | 109.8 → 53.1 | 52% | 96.4 → 40.2 | 0.14 → 0.04 | 71% |
| `basic.xlsx` | 137.1 → 53.1 | 61% | 124.2 → 40.6 | 0.19 → 0.04 | 79% |
| `many-sheets.xlsx` | 82.2 → 52.6 | 36% | 62.3 → 40.0 | 0.44 → 0.38 | 14% |
| `many-slides.pptx` | 85.8 → 41.7 | 51% | 72.8 → 28.0 | 0.20 → 0.16 | 20% |

大きい XLSX は 4 シート × 3,000 データ行 × 8 列、大きい PPTX は 100 スライド × 36 図形。修正前は `58d934b`（PR #58 の main への取り込み `171af3d` と同じツリー）、修正後は今回の変更を含むリリースビルド。

全実行値、raw time 出力、入力・バイナリ・PNG の SHA-256 は [2026-10-06-go-optimized.json](benchmarks/2026-10-06-go-optimized.json) に保存した。

## 原因と変更

### 埋め込みフォントの圧縮

従来は 1 MiB 以下のフォントに Brotli quality 11 と固定の LGWin=22 を使っていた。PPTX の割り当てプロファイルでは、約 214 MB の累積確保のうち約 128 MB が `brotli.(*h10).Initialize` に集中していた。小さなフォントでも、圧縮用の探索木に 32 MiB を確保するためである。この累積確保量はプロセスの RSS とは異なる。

- quality 9 に統一し、圧縮の探索時間を短縮した。文字の輪郭やフォントの内容は変わらない。
- ウィンドウはフォントのデータ長に応じて LGWin=10〜22 の範囲で選ぶ。固定 4 MiB のウィンドウを小さいサブセットにも使う処理をやめた。

| 入力 | BDF: 修正前 → 修正後（バイト） | 増加率 |
|---|---:|---:|
| `basic.docx` | 109,522 → 114,806 | 4.82% |
| `basic.pptx` | 43,500 → 45,704 | 5.07% |
| `basic.xlsx` | 72,032 → 75,121 | 4.29% |
| `many-sheets.xlsx` | 1,672,386 → 1,673,382 | 0.06% |
| `many-slides.pptx` | 185,445 → 186,202 | 0.41% |

### サムネイルの代替フォント読み込み

埋め込みフォントだけで描画できる場合にも、システムの代替フォントを事前に読み込んでいた。調査した文書では、この段階で約 26 MB の追加確保があった。

- 埋め込みフォントで文字が見つからないときにだけ、システムのフォント候補を解決する。
- 汎用の代替候補は cmap の文字対応を調べ、必要な文字を持つものだけ輪郭データを読み込む。
- フォントの優先順位、疑似太字・斜体、ベースライン、文字がない場合の `.notdef` の扱いを維持する。呼び出し元が FONT 命令を再利用しても、遅延した検索条件が変わらないよう値をコピーする。

## 過去の LibreOffice 比較との関係

LibreOffice / Poppler は今回は再実行していない。以下の他実装の値は 2026-09-29 の保存済み結果であり、今回の改善率は上の同日・同一入力による Go 同士の比較から求めた。

| 入力 | Go: 9/29 RSS → 今回 RSS (MiB) | Go: 9/29 時間 → 今回時間 (秒) | LibreOffice: 9/29 RSS / footprint (MiB) | LibreOffice: 9/29 時間 (秒) |
|---|---:|---:|---:|---:|
| `basic.docx` | 121.5 → 70.1 | 0.34 → 0.05 | 161.9 / 93.3 | 0.73 |
| `basic.pptx` | 92.3 → 53.1 | 0.15 → 0.04 | 146.9 / 80.4 | 1.00 |
| `basic.xlsx` | 120.4 → 53.1 | 0.20 → 0.04 | 123.8 / 53.1 | 0.64 |
| `many-sheets.xlsx` | 81.9 → 52.6 | 0.46 → 0.38 | 289.7 / 224.0 | 1.55 |

9/29 の 100 スライド PPTX は RSS 94.2 MiB、footprint 56.8 MiB。ただし正確なコマンドと時間が記録されていないため、過去値との比較は参考にとどめる。

今回の調査前に測った PR #58 の結果は [2026-10-06-go.json](benchmarks/2026-10-06-go.json) に残した。PR #58 では Go testing の B/op が減っても、変換全体のプロセスピークは全体として下がっていなかった。この再調査でフォント圧縮と読み込みの負荷を特定した。

## 条件と再計測

- Apple M3、macOS 27.0.1、Go 1.27.0、darwin/arm64。
- `go build -trimpath '-ldflags=-s -w'` で事前ビルドし、ビルド時間は計測外。
- macOS の `/usr/bin/time -l`。文書・バイナリごとにウォームアップ 1 回を除外し、新規プロセスで 5 回変換。修正前後の実行順を毎回入れ替えた。並行してビルドやテストを実行していない。
- 計測対象は CLI の起動、入力の読み込み・変換、BDF の保存、256 px fit サムネイルの生成・保存。常駐サーバーでの繰り返し処理や OS のファイルキャッシュを破棄した起動は測っていない。
- `/usr/bin/time` の実時間は 0.01 秒単位。短い処理の細かい差や丸められた改善率を過度に解釈しない。
- 小さい 3 文書の SHA-256 は 9/29 の記録と完全一致。
- 大きい 2 文書は元の生成スクリプトと同じ xlsxwriter 3.2.9 / python-pptx 1.0.2 で再生成した。シート XML 3,144,865 バイト、スライド XML 2,655,012 バイトは過去の記録と一致。ZIP のタイムスタンプなどでファイル全体のハッシュは異なるが、今回の修正前後には同じファイルを使用した。
- 9/29 の大きい XLSX は `xlsx_pipeline` の 3 回の中央値。今回は 5 回の中央値。

[benchmark-memory-go.py](../tools/benchmark-memory-go.py) は Go CLI だけを再実行する。修正前後のビルドを用意した場合の例:

```sh
python3 tools/benchmark-memory-go.py \
  --bdf /tmp/bdf-after --revision AFTER_REVISION \
  --compare-bdf /tmp/bdf-before --compare-revision BEFORE_REVISION \
  --input examples/sample-files/basic.docx \
  --input examples/sample-files/basic.pptx \
  --input examples/sample-files/basic.xlsx \
  --rounds 5 --output /tmp/bdf-process-results.json
```

`--input` で大きい文書も追加できる。`--baseline` に 9/29 の比較 JSON を渡すと、保存されている LibreOffice の値も出力に含める。指定した 2 つのバイナリの PNG が一致しない場合は測定をエラーにする。単一バイナリの再計測では `--compare-bdf` と `--compare-revision` を省略する。

## 検証

- `go test ./...`、`go vet -unreachable=false ./...`、変更した経路の race 検査に成功。
- 圧縮の境界サイズで展開後のバイト一致を確認。4 KiB の入力で巨大な作業領域を確保しない回帰テストを追加。
- 埋め込み文字だけでは外部フォントを読み込まず、欠けた文字に必要な代替フォントを順に読み込むことをテスト。優先順位、`.notdef`、ベースライン、呼び出し元の値変更も確認。
- 比較ベンチの 5 文書は、ウォームアップを含む全実行で修正前後の PNG が完全一致。
- 圧縮バイト列と部品ハッシュの変更に合わせて BDF、分割版、暗号化版、segment の fixture を再生成。Go 全テストと npm の 132 テストに成功。
- Chromium headless shell 1194 で既存ハーネスの 115 ケースを修正前後の BDF で描画し、通常描画と Worker 描画の PNG がすべて一致した。macOS で `npm run test:golden` を実行すると保存済みの基準画像との差で 25 件が失敗するが、同じ 25 件が修正前にも失敗する。基準画像と許容値は変更していない。
- `bdf_noconv` での代替フォントの回帰テストと、`bdf_noconv,previewonly` の Go WASM ビルドに成功。
