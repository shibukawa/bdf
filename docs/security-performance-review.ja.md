# パフォーマンス・セキュリティ調査

調査日: 2026-10-06。対象は Go の BDF 読み込み・変換器・ラスタライザ、TypeScript の core/render/viewer、サーバー例、依存パッケージと CI。

入力ファイルのサイズ・数値・参照先を信頼しない前提でコードを読み、問題を再現するテストを追加して修正した。全パッケージの回帰テストも実施した。これは、あらゆる入力や運用環境で問題が起きないことを保証する監査ではない。

## 修正した問題

| 優先度 | 問題と影響 | 修正 |
|---|---|---|
| 高 | 古い画像デコーダに、細工された WebP による過剰なメモリ確保や BMP/WebP のパニックの既知問題がある | `golang.org/x/image` を v0.30.0 から v0.46.0 に更新 |
| 高 | 古い PDF パーサーには、深い入れ子や巨大なストリーム・xref などによる DoS の問題がある | `pdfcpu` を v0.11.0 から v0.16.1 に更新。符号化・デコード済みストリームを各 256 MiB、オブジェクト番号と xref の件数を各 2²⁰ に制限。組み込み設定を使い、ユーザーの設定ファイルを読まない |
| 高 | HTML/Markdown の画像と KiCad の参照ファイルが、`../` やシンボリックリンクで `Options.Dir` の外へ出られる | Go の `os.OpenInRoot` でディレクトリ内に制限。チェック後にリンクが差し替わる競合も避ける。TinyGo ではローカル資源を拒否し、アップロードされた `Files` や data URL を使う |
| 高（サーバー利用時） | HTML/Markdown は文書内 URL の画像を既定で取得するため、サーバーの内部ネットワークにアクセスできる | 4 つのサーバー例で `remote=false` を設定 |
| 中 | 曲線ごとの分割数は有限でも、命令全体の点数や走査線との交差回数が増幅する | 1 命令で展開する点と走査する辺を各 2²⁰、走査線で訪れる辺を累計 2²⁴ までに制限。超過した描画は警告して省略し、後続の描画を続ける |
| 中 | ブラウザで依存を一斉に準備すると、数千件の通信や画像デコードが同時に始まる | 重複を除き、`ensure` の呼び出しごとに 8 件ずつ準備。失敗時も開始したコールバックを待ち、後処理後の資源追加を防ぐ |
| 中 | HTTP Range を無視するサーバーや `fetchSingle` の応答を無制限にメモリへ読む | 全体応答を既定 1 GiB までに制限し、ストリームを途中で停止。第 3 引数で上限を指定できる |
| 中 | 20 万件の画像・Object 参照を関数の引数に展開すると JavaScript の引数数制限で失敗する | `objectDeps` をループで追加する処理に変更 |
| 中 | 画像のヘッダー読み込みのパニックが `imgconv.Decode` の外へ漏れる。幅×高さの乗算もオーバーフローしうる | ヘッダーを含めてパニックをエラー化し、除算で画素数上限を検査 |
| 低 | deflate の上限が `MaxInt64` の場合、`limit+1` がオーバーフローして空データを正常扱いする | 上限まで読んでから 1 バイトを別に検査。flate reader も閉じる |
| 低 | `RangeSource` がヘッダーと manifest の暗号化フラグ不一致を見逃す | `BufferSource` と同じ検査を追加 |

画像デコーダの根拠: [WebP のメモリ確保問題 GO-2026-6222](https://pkg.go.dev/vuln/GO-2026-6222)、[BMP の問題 GO-2026-5031](https://pkg.go.dev/vuln/GO-2026-5031)、[WebP の問題 GO-2026-5061](https://pkg.go.dev/vuln/GO-2026-5061)。PDF の根拠: [再帰深さを制限する上流修正](https://github.com/pdfcpu/pdfcpu/commit/9db810afb52b555ffcae955b32c0be3a73eb53d3)、[pdfcpu v0.16.0](https://github.com/pdfcpu/pdfcpu/releases/tag/v0.16.0)、[v0.16.1](https://github.com/pdfcpu/pdfcpu/releases/tag/v0.16.1)。

## 再現と検証

- HTML: 親ディレクトリへの参照、二重の `..`、外部を指すシンボリックリンクを修正前に再現。修正後は拒否し、ディレクトリ内の `images/../safe.png` は読める。
- KiCad 共通参照: 親ディレクトリと外部シンボリックリンクを拒否し、既存の階層シートの読み込みテストを維持。
- TypeScript: 20 万件の参照で起きる `RangeError` と、64 件が同時に準備される動作を修正前に再現。修正後は重複を各 1 回だけ準備し、同時数は 8 以下。
- HTTP: 上限を超える全体応答で、取得中のストリームがキャンセルされることを確認。
- Go: 画像ヘッダーのパニック、最大整数の展開上限で空データになる問題を修正前に再現。修正後は適切なエラーまたは元データを返す。
- Raster: 複数パスの点数を合算し、曲線の展開と大量の交差を打ち切ること、過大な塗り・線を省略して後の矩形を描けることを確認。
- PDF: 深い配列、1 TiB のストリーム長、約 21 億の xref サイズを持つ小さな入力が変換エラーになり、確保量が 16 MiB 以下であることを確認。

依存の検査は `govulncheck v1.8.0` と npm audit を使用した。Go のスキャンでは到達可能な脆弱性は検出されなかった。モジュール単位では `golang.org/x/crypto/openpgp` の [GO-2026-5932](https://pkg.go.dev/vuln/GO-2026-5932) が報告されるが、このリポジトリは OpenPGP を import していない。スキャン時の Go データベース最終更新は 2026-10-01 で、より新しい PDF の修正は上流の公開情報と実コードでも確認した。npm の依存検査は 0 件。

CI に到達可能な Go 依存の脆弱性検査と、npm の high 以上の検査を追加した。

回帰検証の結果:

- `go test ./...`: 全パッケージで成功。Go の raster の golden 比較と、近道の有無で描画結果が一致する検査も含む。
- `go vet -unreachable=false ./...`: 成功。既存 CI と同じく生成コードに対する unreachable の検査だけ除外。
- `go test -tags bdf_noconv ./imgconv/ ./converter/... ./woff2/`: 成功。
- `go test -race . ./converter/html ./converter ./raster/imagebdf`: 成功。
- `npm test`: 132 件成功。
- PDF のテスト入力 11 件を CLI で再変換し、既存 BDF とバイト単位で一致。
- 通常の Go で `bdf_noconv,pdfonly` の WASM ビルドに成功。
- TinyGo 0.42 で HTML/PDF のカスタム WASM をビルド（約 130 秒、8.1 MB）。ヘッドレス Chrome 上で Worker の起動と両形式からの BDF 変換に成功。

## 互換性と運用条件

- 文書の外のファイルを参照していた入力は、その資源を読めなくなる。必要な資源を文書ディレクトリの内側へ置くか、明示した `Options.Files` で渡す。TinyGo のブラウザ変換器ではローカルファイルを使わない。
- HTML/Markdown ライブラリのネットワーク取得は従来どおり既定で有効。信頼しない文書を扱う独自のサーバーでも `NoRemote` / `remote=false` を指定する。取得を必要とする場合は `Fetch` で接続先・リダイレクト先を制限する。
- `ensure` の 8 件制限は呼び出し単位。複数ページを並行して準備すれば合計は増えるため、呼び出し側でもページの並行数を制限する。
- 上限は資源ごとの制限で、プロセス全体のメモリや実行時間を保証するものではない。信頼しない大量の入力を扱うサービスは、変換ジョブの同時数、入力サイズ、プロセスのメモリと実行時間にも上限を設ける。
- TinyGo 0.42 の不足 API は、ビルド時に一時コピーした pdfcpu に互換処理を適用する。乱数は同じ 160 ビットの暗号学的乱数を使い、ファイル同一性が必要な操作は拒否する。ブラウザ変換はメモリ上の入出力を使用する。
- 新しい文字幅ライブラリの 2 MiB テーブルを TinyGo 0.42 が定数化すると、コンパイル時間が二次的に増える。TinyGo 用の一時コピーではテーブルの初期化を起動時に行い、完了を待ってから次の初期化へ進む。文字幅や初期化後の並行処理は変更しない。変更したコピーに対して文字幅ライブラリ自身のテストも成功した。
- ローカルの `gosec` は型解析の互換性エラーで完走できなかった。`go vet`、公式依存スキャン、コードの確認、回帰テストの結果を使用した。
