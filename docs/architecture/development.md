# Building and testing

Go 1.27 or later, and Node.js for the TypeScript packages and the demo site.

## Go

```sh
go test ./...                          # every package
go run ./cmd/bdf demo out.bdf          # write the fixture document
go build -tags bdf_noconv ./...        # without the image/WOFF2 codecs (the browser build's profile)
GOEXPERIMENT=simd go build ./...       # Go 1.27, amd64/arm64: SIMD codec variants (amd64 needs AVX2)
```

`bdf_noconv` leaves out the codecs the browser doesn't need (see [design.md §2](../design.md#2-go-と-wasm-について)). CI builds and tests this configuration separately, so a change that only works with them compiled in won't surface until CI unless you check it locally too.

## TypeScript

```sh
npm ci
npm run build           # tsc -b packages/core packages/render
npm test                # node --test on packages/*/test/*.test.mjs (builds first)
npm run test:golden     # render fixtures with Chromium, compare against testdata/golden/*.png
npm run test:golden:update  # replace the golden PNGs with what's rendered now
```

Golden tests need a pinned Chromium build (`playwright-core`'s headless shell) — the full Chromium binary rasterizes text slightly differently, so goldens only match the exact build they were made with. Get it with `npx playwright-core install chromium`, or point `CHROMIUM_PATH` at an equivalent headless shell already on the machine.

## Regenerating fixtures

`npm run testdata` rebuilds everything under `testdata/` from the source files under each `converter/*/testdata/` (needs Go); CI checks the result byte-for-byte against what's committed. Each format's sample *inputs* (the `.pptx`, `.dxf`, `.epub` … files themselves) are generated by their own script, most needing Python:

```sh
npm run test:pptx:gen      # python-pptx, msoffcrypto-tool
npm run test:xlsx:gen      # openpyxl
npm run test:dxf:gen       # ezdxf
npm run test:kicad:gen
npm run test:musicxml:gen  # (run from converter/musicxml/testdata)
# … one per format; see package.json's scripts for the full list
```

## Running a viewer locally

```sh
npm run demo         # http://127.0.0.1:8765/examples/viewer/.out/ — the viewer alone, opens any .bdf under the repo via ?src=
npm run site         # builds site/dist: the full site (top page, viewer, thumbnail/text pages, docs), needs Go
npm run site:serve   # npm run site, then serves it
node examples/viewer/serve.mjs   # same as npm run demo
```

`?src=` points the standalone viewer at a `.bdf` path in the repository, e.g. `http://127.0.0.1:8765/examples/viewer/.out/?src=/testdata/drawio/multipage.bdf`; `&layout=spread` opens it as a book. `BDF_SITE_FONTS=dir1:dir2 npm run site` publishes those fonts with the site instead of the default test fonts.

## Rendering or inspecting an arbitrary `.bdf`

```sh
node test/render.mjs out.bdf pngdir/     # render every page to PNG with headless Chromium
go run ./cmd/bdf ls out.bdf              # part list
go run ./cmd/bdf render -page 2 out.bdf page2.png  # render one page, in pure Go (no browser)
```

## Matching CI's output exactly

CI's `testdata is up to date` step compares `bdf generate` output byte-for-byte on `ubuntu-latest` (amd64). Go's floating-point contraction differs by architecture, though, so the same command run on Apple Silicon can produce a few different low bits in an object's bounding boxes. Cross-compile with `GOARCH=amd64 go build` and run that binary under Rosetta to reproduce CI's bytes locally, before assuming a diff is a real regression.

New golden PNGs raise a separate concern: they need the same headless-shell Chromium build CI uses, and running the golden tests inside a matching container (`mcr.microsoft.com/playwright:v1.56.1-noble`, or `node:24-bookworm` with Chromium installed) reproduces that build.

See the [API reference](../api.md) for what each package and command exposes, and [The bdf command](cli.md) for `bdf`'s subcommands. Current fixture, rendering, and browser-conversion results are in the [conversion quality report](../quality.md) (Japanese).
